# L3调度与任务创建

## 先把 L3 放回整条记忆链路

L3 核心记忆不会直接读取外部会话，也不会越过 L1、L2 去读原始消息。它的输入是已经发布成功的 **L2 场景当前版本**。

L2 的 CREATE、自动 UPDATE，以及 MERGE 后保留下来的当前场景成功发布时，会在 `projection_change` 里追加一条 `memory-current`、来源类型为 `L2`、操作为 `UPSERT` 的变化。RETIRE 和被 MERGE 吸收的场景写入 `DELETE`，不会进入这条普通 L3 自动归纳链路。后台高层运行时每秒轮询一次这些 `UPSERT` 变化，满足 L3 到期条件后，把当前活跃 L2 场景版本冻结成一条 L3 Evolution Job。

我按后端实际调用顺序拆成下面几步，小伙伴看源码时可以一直对照这条线：

1. `JdbcHighLevelAutomaticSchedulingStore.candidates()` 按 L3 游标找出尚未消费的 L2 投影变化。
2. `DefaultHighLevelAutomaticScheduling.scheduleDue()` 判断候选是否到期，并读取记忆库授权版本。
3. `DefaultL3EvolutionScheduling.schedule()` 对当前 L2 版本 ID 排序，计算输入摘要，创建或复用 L3 Job。
4. `JdbcL3EvolutionSchedulingStore.create()` 再次确认每个 L2 版本仍是活跃场景的当前版本。
5. `JdbcHighLevelAutomaticSchedulingStore.register()` 在事务里登记运行态，并把 L3 自动游标推进到这批变化的序号。
6. 后台下一步才会去认领 Job、调用模型；本篇先讲到“任务已经排队”。
