## 三种接入，各管一件事

我在控制台里第一次看到三个接入入口的时候有点懵——看着都跟"记忆"有关，不知道是不是装一个就都有了。

实际上它们是**三件独立的事**，可以单独装、单独用，也可以一起用。装了一个不会顺带把另外两个打开。

<Tabs>
<TabItem value="capture" label="把对话存进来" default>

**控制台里叫：自动会话采集**

装上之后，你在工具里和 AI 完成的问答会被保存到项目里，成为以后整理经验的原料。

- **它会做什么：** 保存你的提问和 AI 的完整回答，一轮一轮地交到项目里。
- **权限：** 只能提交，不能读取项目里已有的经验。
- **装之前要知道：** 装好**不会自动开始采集**，需要你在本地明确启用。暂停之后恢复不会补采暂停期间的对话。

</TabItem>
<TabItem value="recall" label="让 AI 每次带上项目经验">

**控制台里叫：自动记忆召回**

装上之后，你每次提问，工具会先把这次问题相关的项目经验取出来，放到 AI 处理这轮对话的时候一起看。

- **它会做什么：** 在你按下回车之后、AI 开始回答之前，去找这个项目里相关的经验。
- **权限：** 只读。它只取经验，不会往项目里写东西。
- **装之前要知道：** 需要项目里已经有可用的、跟当前问题相关的经验，才有东西可取。

</TabItem>
<TabItem value="mcp" label="在对话里按需调用">

**控制台里叫：MCP 外部接入**

这个给的是"我需要的时候去查一下"的能力：让 AI 工具在对话过程中主动搜索、读取、保存记忆。

- **它会做什么：** 提供一组记忆操作，工具按你的要求调用；也可以在你确认之后把某段内容存进来。
- **权限：** 创建连接时可以选**只读**（召回、搜索、导出）或者**读写**（再加上捕获、反馈、导入）。
- **装之前要知道：** 装它不会启用自动保存和自动召回。想同时要，得分别装。

</TabItem>
</Tabs>

:::tip 三种凭据是分开的，这一点挺省心
每条接入有自己独立的凭据，可以单独轮换、单独撤销。哪天你觉得"自动保存先关掉吧"，撤销采集连接就行，**不会连带把召回和 MCP 也弄停**。反过来也一样。
:::

### 按什么顺序装比较顺

如果拿不准从哪儿开始，我建议**先装自动召回**。理由很实在：召回是只读的，不会往项目里写任何东西，心理负担最低；而且它能让你立刻看到"拿到的经验长什么样"。

不过光装召回，项目里可能是空的。所以更常见的起步方式是这样：

1. **建一个项目**，起个能认出来的名字。
2. **自己手动加几条确定没问题的规则**，或者装采集跑一轮真实对话。
3. **装自动召回**，新开一个相关任务，看看这次是不是真的带上了那条规则。
4. 确认流程顺了、内容也靠谱，**再开自动采集**，让它慢慢从日常对话里攒。

顺序反过来的后果我也踩过：一上来就开采集，几天之后攒了一堆内容，但你还没看过它们准不准，AI 用起来的效果就不稳定。

## 装的时候会发生什么

我一开始以为要自己编辑配置文件，实际不是。你在控制台里创建连接，会拿到一段**一次性安装代码**，然后在你的业务项目目录里跑一条安装命令，把它粘进去就行。

大概是这样几步：

1. 在控制台的接入页面选好项目，**创建一条个人连接**。创建时要选有效期（1 到 90 天）和权限范围。
2. 页面会给出**安装命令和一段安装代码**。安装代码里含你的凭据，所以页面上会提醒你别提交到 Git、别分享。
3. 在**你的业务项目根目录**里执行安装命令。终端会提示"粘贴一次性安装代码"，粘进去按回车。**输入是隐藏的，看不到字符是正常的。**
4. 安装器会**列出它准备改哪些文件**，你确认之后才真正写入。
5. 装完**完全退出并重启客户端**——配置是启动时读的，已经在跑的会话不会生效。

装完之后，客户端那边一般还需要你确认一次（比如信任这个项目的配置），然后就能在对话里验证了。控制台的接入教程里，每种方式都有一份六步的指引：准备环境、安装连接、启动启用、验证、排查问题、停用移除。**遇到问题先看"排查问题"那一节**，比到处猜快得多。

### 装到什么程度算好了

有个小细节值得提前知道：安装命令里有个自检。

**它只检查本地**——项目绑定和客户端配置读得到就行，**不会去连服务端**。所以"自检通过"说明本机的配置是对的，不代表服务端那边一定通。这两个是分开的，排查的时候别混。

## “改别人的配置文件”这件事有多麻烦

这部分是我做的时候花时间最多、也最容易被低估的地方。表面上看，安装就是"往客户端的配置里加一段"，但真做起来要处理的是一连串现实问题。

### 每个客户端的配置方式都不一样

三个客户端，三种完全不同的接入机制：

| 客户端 | 召回怎么实现 | 采集怎么实现 |
| --- | --- | --- |
| Codex | 提交提问时的钩子 | 一组会话生命周期钩子 |
| Claude Code | 提交提问时的钩子 | 一组钩子，需从专用入口启动 |
| OpenCode | 插件 | 插件 |

所以驱动是分开写的，每种都按它自己的机制来。

### 用户原来的配置不能被弄坏

这是我自己最在意的一条。**装这个工具不能把用户原有的配置搞乱。**

所以安装器做的是**合并**而不是覆盖：读出现有配置，只加自己需要的那部分，并且用自己的标记把新增内容圈起来——将来卸载时只删标记内的部分，别的一律不动。

这套做法解决了几个很具体的问题：

- **装两次不会变成两份。** 重复执行安装是安全的。
- **卸载不会误伤。** 只清自己写进去的那段，用户自己的配置留着。
- **互相冲突能被发现。** 如果发现已有配置跟要写入的内容矛盾，会提示而不是硬写。
- **多个客户端可以共存。** 同一个目录装了 Codex 又装 Claude Code，卸载其中一个时，**项目绑定和你的个人凭据会保留**（因为另一个还在用），只摘掉那个客户端的配置。

:::tip 这类"往别人家里装东西"的活儿，值得单独学
“怎么安全地修改用户既有的配置文件”是工具类项目绕不开的问题——CLI 工具、代码生成器、脚手架、IDE 插件都会遇到。

这里给出的答案是一整套可复用的思路：**标记化写入、幂等安装、限定范围的卸载、冲突检测**。这套东西在面试里讲得清、在别的项目里直接用得上。
:::

### 版本差异不能假装不存在

AI 客户端的更新速度很快，接口还可能变。这个项目没有假装"支持所有版本"，而是给出了明确的处理方式：

我把验证过的版本写进配置里，同时**允许其他版本继续尝试**——读取本机实际版本，照常工作，但如实记录真实版本号。这样做的结果有两点：

- 客户端小版本升级之后，功能**不会静默失效**（这是最糟的情况：用户以为在记，实际什么都没记）。
- 出了问题能查到当时用的是哪个版本，而不是只能猜。

控制台里对这件事说得很直白：哪些版本验证过、哪些场景能用、带什么参数启动会失效——**都写在教程里，不藏在代码注释里**。

:::info 这一条在面试里比"支持 N 个客户端"更值钱
说"支持三个客户端"只是数量；能说清楚**版本差异怎么处理、验证到什么程度、不支持的时候怎么退化**，才是工程能力。
:::

## 目前真的能用的客户端

这部分我想说得直白一点，因为介绍页面上很容易让人误会：**目前做好接入的是 Codex、Claude Code、OpenCode 这三个。**

| 客户端 | 我做过的验证 | 需要留意的地方 |
| --- | --- | --- |
| Codex | 在 macOS 上按具体版本验证过 | 项目级别的配置需要你确认信任；换版本可以继续试 |
| Claude Code | 在 macOS 上按具体版本验证过 | 采集必须从它专用的启动入口进；普通启动只有召回能用 |
| OpenCode | 在 macOS 上按具体版本验证过 | 要在正常的交互模式里用；带某些参数启动会禁用 |

有三件事我不想含糊：

- **只在这几个客户端上验证过，而且是在 macOS 上。** 其他版本不是不能用，是会"按你本机实际的版本继续尝试"，但我没验证过，不能替它打包票。
- **只在正常交互式的用法里验证过。** 那些一次性的、脚本式的、非交互的用法（比如把工具当命令跑、接管道处理）不在支持范围里，装了也不会生效。
- **自动保存和自动召回是两个独立的东西，可以分别装、分别停。** 你想只留召回、不开采集，完全没问题。

:::info 别看到图标就以为都能用
介绍页的架构图上画了一圈生态工具的图标，那是**我想要支持的方向**。真正做好驱动、验证过的只有上面这三个。什么工具能不能用，以控制台接入页面里给出的教程为准。
:::

## 服务不可用的时候，你自己的活不会被耽误

这个是我当初最关心的问题：要是这个服务挂了，我是不是连代码都写不了了。

不会。**它没有挡在你的工作流中间。**

- **取经验失败时**，这一轮对话照常进行，只是不带项目经验，你会在会话里看到一行提示，说明这次没注入。
- **存对话失败时**，内容会先在**你自己的机器上排队**，等服务恢复再投递。
- **客户端本身的任务不受影响。** 服务出问题的时候，你原来在用的工具该怎么跑还怎么跑。

### 本机这个队列是怎么排的

这个"先在本地排队"的机制，比它看起来要讲究。它处理的是**服务暂时不可用**这个必然会发生的情况：

<Tabs>
<TabItem value="retry" label="失败了怎么办" default>

投递失败的会留在队列里重试，重试间隔从短到长逐步拉开——**避免服务刚恢复就被一堆重试请求冲垮**。

有些错误是重试也没用的（凭据不对、内容被拒、格式有问题），这类直接判定为不可重试并单独标记，不会一直占着重试名额。

</TabItem>
<TabItem value="limit" label="能存多少、存多久">

队列有明确上限：**大小、条数、保留天数都有约束**。所以它是个缓冲，不是无限仓库。

超过上限时新的内容会被拒绝并计入统计——这是有意为之：**宁可明确告诉你"这里满了，去处理一下"，也不要悄悄堆到把磁盘撑满。**

</TabItem>
<TabItem value="recover" label="客户端崩了、断电了">

队列里的每条内容都有"正在投递"的租约标记。如果投递到一半客户端被杀掉，那条内容会卡在"正在投递"状态。

恢复时，**过期的租约会被自动放回待投递队列**——所以不会出现"这条内容永远投不出去"的死角。

如果发现有别的进程残留的锁，也会按进程存活情况清理掉，不会互相堵住。

</TabItem>
</Tabs>

:::note 待补图 06：一次提问里认知引擎做了什么
**形式：时序或流程示意。** 左边是"你"，中间是"你的 AI 工具"，右边是"认知引擎"。画出：你提问 → 工具先向引擎要相关经验 → 引擎返回（或返回"没有合适的"）→ 工具带着这些经验处理问题 → 回答完成后把这一轮交回引擎保存。

在"要经验"这条线上标一个"超时/失败 → 本轮继续，不带经验"，在"交回"这条线上标一个"服务不可用 → 先存本机队列，稍后投递"。

**想让读者看明白：** 引擎是在工具的两侧各插一次——回答前取、回答后存——而不是接管整个对话。任何一侧失败都不阻断中间那步。
:::

我想强调这一点：**它是个锦上添花的东西，不该成为你干活的单点故障。** 设计上也是这么做的。

反过来说，因为本地队列有上限，如果你长期没管它，超出上限的新对话就会被拒掉——所以偶尔看一眼状态是有必要的。

## 关于隐私和权限，我自己的几条使用习惯

权限这件事控制台做得很细，但细也意味着你得自己知道在选什么。分享几条我自己的做法：

- **写入权限只给信得过的工具。** MCP 连接创建时能选只读或读写，权限大一圈，风险也大一圈。不确定就先只读。
- **安装代码等于凭据，当密码对待。** 别粘到聊天窗口、别提交进仓库。
- **每条连接的用途分开命名。** 控制台里建议"用项目或用途命名"，我很赞同——过两个月你只会看到一串连接名，"订单项目开发 / 只读"这类名字能救你。
- **凭据有有效期，到时候要换。** 到期需要新建连接；有效期内也可以轮换。这是安全上的好事，但别忘了它。

再补一条我一开始没意识到的：**能用项目经验，不等于能看别人的原始对话。** 这两件事是分开授权的。团队场景下这一点尤其重要，具体在[内容维护与团队共享](/agent-up-memory/overview/maintenance-and-sharing)里说。

:::tip 客户端参数不能"换个项目"
有个安全细节值得提一句：工具调用的时候，客户端**不能通过参数把请求切到别的项目上去**。项目和权限是服务端从你的连接里解析出来的，不由客户端指定。

这类"身份和范围由服务端定、不由调用方传"的做法，是多租户系统里最基本的防线。
:::

## 不想用了怎么退

每个接入方式都提供卸载，而且做得挺克制：**它只清掉自己写进客户端的那部分配置**，不会动客户端别的东西。

如果同一个目录连了好几个客户端，卸载其中一个时，**项目绑定和你的个人凭据会保留**（因为别的客户端还在用），只是把那个客户端的配置摘掉。

如果是要整个停用，撤销连接就可以；同时记得**把已经装到本机客户端里的配置一并清掉**。撤销连接只影响服务端这一侧。

:::tip 暂停不住手，卸载才彻底
控制台里能暂停采集，本机也能暂停投递。但"暂停"只是不再往项目里送新内容，**配置还留在客户端里**。哪天你想彻底不留痕迹，用卸载命令把它清掉。
:::
