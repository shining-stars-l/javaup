## 这个项目能给面试带来哪些具体话题

<div className={styles.lead}>
  <span className={styles.eyebrow}>让项目经历有具体内容可讲</span>
  <p><strong>一个业务需求，可以继续讲到 AI 内容处理、后台任务、权限和多工具接入。</strong>智能体认知引擎的主线很容易说明：让 Claude Code、Codex、OpenCode 在同一个业务项目下共享已经积累的经验，减少换工具后的重复交代。</p>
  <p>围绕这条主线，小伙伴可以结合自己实际完成的学习和改动，讲清功能怎样工作、为什么这样设计、遇到异常怎么办，以及怎样确认结果。</p>
</div>

面试介绍项目时，如果开头就列一串功能和技术名称，对方很难知道你到底解决了什么问题。我建议先讲一个具体使用场景，再选自己最熟悉的两三个部分深入。

这个项目既有容易理解的产品价值，也有能够继续追问的设计细节。你可以组织重点：AI 应用方向多讲内容怎样形成和使用，后端方向多讲状态、重复、并发和权限，涉及工具集成时再讲不同客户端怎样配合。

## 先把项目给介绍清楚

### 开头把用户、问题和使用方式要说明白

下面是一段表达结构示例。实际使用时，应把最后一句改成自己真实研究、实现或修改过的部分。

<div className={styles.example}>
  <span className={styles.speaker}>项目介绍示例</span>
  <p>“我学习并实践了一个跨 AI 工具的项目记忆系统。用户在 Claude Code、Codex、OpenCode 中做同一个业务项目时，执行对话里的规则和经验可以整理到一起，后面的工具处理相关任务时，再按项目查找这些内容。”</p>
  <p>“我重点研究了其中的〔自己实际完成的部分〕，做了〔实际改动或验证〕。例如〔一个能够展示的具体结果〕，这里涉及到〔自己能够解释的设计问题〕。”</p>
</div>

这样介绍之后，对方先知道项目为什么存在，也知道你参与到哪里。接着再展开某项设计，会比从功能清单开始更容易沟通。

### 接下来选择自己能讲清楚的内容

| 你准备突出什么 | 可以从哪个具体问题切入 | 能继续展开的内容 |
| --- | --- | --- |
| AI 内容处理能力 | 一段执行对话怎样变成可用经验 | 筛选、去重、人工确认、来源和版本 |
| 后端可靠性 | 同一段问答重复发送，应该怎样处理 | 来源身份、重复判断、保存结果、失败恢复 |
| 检索和结果选择 | 查到了很多内容，为什么只提供一部分 | 相关性、当前权限、有效版本和长度 |
| 多用户业务设计 | 两个成员能共享什么，不能自动共享什么 | 项目资格、个人连接、原始对话和管理权限 |
| 多工具接入 | 三个不同工具怎样共用一个项目 | 各工具差异、完整问答识别、项目绑定 |

这几条线不需要一次讲完。先选择自己有演示、有记录、也能解释异常情况的部分，面试时再根据问题深入。

:::note 待补图 08：项目面试讲述路线图
**形式：思维导图。** 中心是“同一业务项目跨 AI 工具共享经验”，向外分成业务场景、本人完成的工作、关键设计、异常处理、验证结果五个分支。每个分支带一个简短例子，例如人工规则保护、重复发送检查等。

## 话题一：不同 AI 工具怎样共享同一个项目的经验

### 可以从业务项目与工具的关系讲起

工具会变，业务项目仍然是同一个。用户在 Claude Code 中讨论订单、在 Codex 中实现报表、在 OpenCode 中检查问题，这些问答都需要明确属于哪个项目。

项目把连接与业务项目绑定，将完整问答作为来源保存，再整理成可用记忆。后续工具根据当前任务，查找自己有资格使用的项目经验。各工具继续管理自己的会话和任务执行。

面试里可以用“订单报表”的例子讲：前一个工具确认过的日期要求怎样留下来，后一个工具怎样取得有关内容。如果自己已经做过跨工具演示，就可以拿出实际记录，而不是只说“支持多个工具”。

### 值得继续准备的追问

- 当前工具怎样确定正在使用哪个业务项目？
- 一次未完成的回答，能不能直接当成完整问答保存？
- 同一项目的多个工作目录，怎样继续使用同一份经验？
- 工具版本或运行方式不支持时，系统怎样表现？

这些追问能体现你是否理解接入前后的完整行为。展示时还应区分“记忆已经提供给工具”和“工具最后正确采用”，两者要分别检查。

## 话题二：用户改过的规则，怎样避免被自动整理覆盖

### 用一次具体变化说明为什么要保护人工内容

比如自动整理得出“报表统一采用自然月”，用户手动补充“客户定制报表可以使用约定周期”。下一次模型如果只读到普通报表的讨论，就可能再次生成没有例外条件的版本。

如果不区分人工内容和自动内容，用户补充的业务判断就容易丢失。项目会根据当前版本的来源采取不同处理方式，自动更新遇到人工版本时转成待确认建议，相关合并也有保护检查。

这里可以讲清楚三个点：为什么要区分来源，为什么建议和正式内容需要分开，以及用户处理建议时为什么还要检查当前内容是否又发生过变化。

<div className={styles.example}>
  <span className={styles.speaker}>适合准备的一次验证</span>
  <p>在练习环境中先形成一条自动记忆，手动补充例外条件，再触发相关整理。检查当前正文是否仍保留人工修改，以及是否产生了需要确认的建议。</p>
  <p>如果要继续深入，可以在建议产生后再次修改正文，观察旧建议会怎样处理。最终讲的是实际观察到的结果及原因。</p>
</div>

这个话题还可以扩展到自动摘要、机器生成标签等业务。你可以说明类似的人工维护问题为什么会出现，以及本项目的处理方式能提供什么参考。

## 话题三：网络失败后重试，为什么不能多记一遍

### 先分清“没有成功”和“没有收到确认”

客户端发送一段问答后超时，有可能服务端没有收到，也有可能服务端已经保存，只是返回的确认没有到达。客户端单看超时，无法把这两种情况完全区分开。

项目通过来源身份和修订信息判断同一份输入，处理重复投递；客户端还有有限暂存和重试能力。这样可以把网络失败和业务内容身份分别处理。

面试时值得讲的是依据是什么：同一个用户又说了一次相似的话，和同一份问答因超时重发，并不是同一种业务情况。只比较正文是否相同，不足以解释这些差别。

### 保存对话和完成记忆整理，也需要分别看待

对话接收之后，还有后台处理。已经收到问答，不代表模型已经完成提取，更不代表后续 AI 已经使用了它。

你可以继续讲为什么这些阶段要有自己的状态，整理失败如何查看，以及哪些相关保存动作需要作为一个整体完成。这样，重复处理、数据保存和后台任务就有了明确的业务背景。

| 可以准备的情况 | 要记录的结果 |
| --- | --- |
| 同一份输入重复投递 | 系统是否识别重复，返回结果怎样变化 |
| 接收成功但整理失败 | 对话是否保留，处理记录怎样显示 |
| 服务短暂不可用后恢复 | 暂存内容处于什么状态，重试怎样推进 |
| 暂存达到限制 | 是否停止继续接收，用户怎样发现问题 |

## 话题四：怎样判断给 AI 的内容是合适的

### 相关性只是其中一个条件

用户问“导出的收入不对”，系统可能找到收入计算、订单取消、日期范围等记录。它们都可能有帮助，但还要继续检查：记录现在是否有效、用户是否有资格读取、提供的内容是否超过限制。

项目支持关键词查找，配置相应模型后还可以结合意思相近的表达，并对结果合并、去重、筛选和控制长度。

讲这部分时，可以选一个具体任务，解释为什么某条记忆被保留、某条被排除。即使是同一句提问，用户权限或记忆版本发生变化后，结果也可能不同。

### 用实际结果说明筛选是否合理

可以准备几种相近提问，检查找到的内容；再停用其中一条记忆，确认后续使用情况。这样能够同时讲到查找能力和业务状态检查。

:::tip 面试里可以继续展开的设计选择
为什么需要几种查找方式配合，为什么找到的记录还要检查当前版本，长度有限时怎样选择内容，以及部分查找失败时怎样保留真实状态。这些都适合用本项目里的实际过程说明。
:::

## 话题五：团队共享之后，权限怎样继续控制

假设项目开放给团队，两位成员分别用不同工具处理任务。他们可以使用允许共享的项目经验，但不会因为加入项目就自动获得对方原始对话的查看权，也不一定都有修改内容的资格。

讲权限时，可以从这几个操作出发：使用一条经验、查看它的原始讨论、修改正文、管理项目。它们涉及的资源和资格不同，不能只用“已经登录”来决定。

接着再考虑状态变化。成员退出团队、账号停用、项目暂停或收窄开放范围之后，之前建立的连接还在，后续访问也必须按当前资格判断。

这个话题适合展示你对权限长期有效性的理解。可以用两个测试账号演示范围变化前后的访问结果，让设计有具体行为支撑。

## 把学习过程整理成能在面试里使用的材料

### 准备一份自己讲得清楚的记录

我建议边学习边留下四类材料：

1. **使用演示。** 能按顺序展示输入来自哪个工具、属于哪个项目、形成什么内容，以及后续怎样使用。
2. **设计说明。** 选一两个重点，写清面对的问题、选择的做法和理由。
3. **验证记录。** 记录正常和异常条件，说明观察到什么，仍有哪些范围没有验证。
4. **个人改动。** 如果做了二次开发，保留需求、实现前后的行为变化和相关检查结果。

这些材料能帮助你把项目经历讲具体。被追问时，也更容易回到自己真正研究过的部分。

### 写简历时，把范围和结果说准确

下面是可以参考的组织方式，空缺部分要根据个人实践填写：

<div className={styles.example}>
  <span className={styles.speaker}>学习实践的表达结构</span>
  <p>“围绕跨 AI 工具共享项目经验，完成了〔实际跑通的流程〕，重点研究〔具体功能〕。通过〔验证方式〕检查了〔实际观察到的行为〕，并独立完成〔真实改动，没有就不写〕。”</p>
</div>

| 你的实际投入 | 可以重点写什么 |
| --- | --- |
| 理解并运行了完整流程 | 实际接入过的工具、保存与使用过程、观察到的结果 |
| 深入验证了某一项设计 | 人工保护、重复处理、权限变化等具体行为及验证方式 |
| 完成了独立改动 | 为什么要改、改后发生什么变化、怎样验证 |
| 做过性能或规模测试 | 真实环境、数据规模、方法和测量结果，说明适用范围 |

没有测量的数据就不写比例，没有真实经历就不写企业上线或独立负责全部模块。描述准确，反而更容易应对围绕细节的继续提问。

项目能提供丰富的准备材料，面试时能讲到多深，还要看自己实际理解和验证到哪里。先选择两三个熟悉的功能，把正常过程、一个异常情况和自己的取舍讲清楚，再逐步扩展。

如果还没确定深入哪个部分，可以回到[项目亮点与实际价值](/agent-up-memory/overview/highlights)选择感兴趣的场景，再按[学习收获](/agent-up-memory/overview/what-you-will-learn)里的练习目标开始动手。
