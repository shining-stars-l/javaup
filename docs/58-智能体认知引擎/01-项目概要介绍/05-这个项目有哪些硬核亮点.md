## 亮点一：记忆分了四层，而且能往上长、往下退

**要解决什么问题。** 如果只往库里堆一条条孤立规则，攒到几百条之后没人愿意看，AI 拿到的也全是碎片。但如果只留一份"总结"，你就失去了原话——出了错根本没法追。

**难在哪。** 浓缩和可追溯是矛盾的：越浓缩越好看，但越难核实。很多项目只能二选一。

**怎么做的。** 项目把内容分成四层，每层职责不同：

| 层次 | 职责 | 举例 |
| --- | --- | --- |
| 原始对话 | 一字不改的原文 | 那几轮讨论金额的对话 |
| 记忆条目 | 可独立使用的单条内容 | 金额按分保存和计算 |
| 场景记忆 | 同一件事的相关条目归组 | 退款相关的一整组要求 |
| 核心记忆 | 跨场景归纳出的稳定做法 | 订单/支付/退款统一遵守的金额规则 |

关键在于**越往上越浓缩，但下面几层一直都在**。真要追问"当初为什么这么定"，一路能回到原话。

**更值得看的是它会"往上长"也"往回退"。** 底层内容变化了、失效了、被删了，上层的结论会跟着重新处理。上面那张表描述的**是一条会跟着上游变化自我修正的演化链**，而不是一份静态的分级存储。

:::tip 这一条为什么值钱
“分层”谁都会说，但**让分层之间保持一致性**才是工程难点。能讲清楚"上游变了，下游怎么退、怎么重算"，比画一张分层图有说服力得多。
:::

## 亮点二：大模型的输出，被当成不可信输入来对待

**要解决什么问题。** 记忆提取要的是结构化的结果——这条是什么类型、来自哪几句话、该存还是该合并。但大模型的输出**天生不稳定**：字段可能少、类型可能错、格式可能飘。

如果直接把模型返回的东西写进数据库，线上的表现就是：偶尔插进去一条内容为空的记忆，偶尔因为一个字段格式不对整个任务失败。

**难在哪。** 你不能控制模型怎么回答，但你必须保证系统只接受合法内容。

**怎么做的。** 项目在几处都做了同样的事：**把模型输出当成外部输入来校验**。

- 要求结构化输出，并且**在模型注册时就验证它具备这个能力**，不具备的模型不让绑定到需要它的用途上。
- 返回内容**按严格格式解析**，字段缺失、类型不对、引用了不存在的内容，一律判定为无效。
- 校验不通过就是任务失败，**不会带着半个结果往下走**。

**还有一个细节我挺喜欢：模型能力在真正调用的时候会再检查一次。** 不是只在配置的时候查过就算——因为模型服务可能改配置、可能被停用。这样能挡掉"配置时好好的，跑起来才发现不支持"的情况。

:::tip 这一条的面试价值很高
“怎么让大模型输出稳定可用”是现在做 AI 应用必问的问题。能说出**结构化校验 + 能力前置验证 + 调用时复查**这套组合，比只说“用 prompt 约束它”要扎实。
:::

## 亮点三：模型按用途绑定，而且钉住版本

**要解决什么问题。** 一个记忆系统里，不同环节对模型的要求完全不同：

| 用途 | 要干什么 |
| --- | --- |
| 记忆提取 | 从对话里挑出候选内容 |
| 记忆去重 | 判断候选和存量记忆的关系 |
| 场景整理 | 把相关条目归组 |
| 核心归纳 | 跨场景总结稳定做法 |
| 向量化 | 把文本转成向量供检索用 |

用同一个模型硬扛全部环节，效果和成本都不划算——有的环节需要理解能力，有的只需要稳定输出。

**难在哪。** 一旦允许分别绑定，就带来新问题：模型换了、升级了，之前跑过的结果怎么算？同一个索引里的向量还兼容吗？

**怎么做的。** 允许为每个用途单独选模型，并且**绑定的是具体版本**。这一条带来几个明确的行为：

- 换了模型之后，**已有的任务不会自动换用新模型**，避免历史结果和新结果混在一起。
- 处理结果里记录了**当时用的哪个模型版本**，所以追溯的时候能说清"这条是哪个模型生成的"。
- 向量化这一环还多一层检查：**生成文档向量和查询向量的模型必须匹配**（同一个模型版本、同样的维度、同样的归一化方式）。不匹配就不能混用——这是向量检索里最容易出错、又最不容易发现的一类问题。

**还有就绪检查。** 控制台会明确告诉你哪些用途还没绑上模型，而且原话写得很实在："在此之前收到的对话只会入库，不会生成长期记忆。"

:::info 这一条特别值得学
“多用途分别绑定模型 + 钉住版本 + 兼容性校验”这套设计，不只适用于记忆系统。**任何把大模型接进业务流程、又需要结果可追溯的系统，都要面对同样的问题。**
:::

## 亮点四：两路检索融合，而且不会把上下文撑爆

**要解决什么问题。** 查找相关经验听起来简单——搜一下不就行了。但实际会碰到两类失败：

- **按关键词搜**：用户问"退款怎么算"，但记忆里写的是"金额按分处理"，字面对不上就搜不到。
- **按语义搜**：意思能对上，但有时候精确的术语、代码标识符反而被语义模糊掉了。

**难在哪。** 两路检索的结果**没法直接比较**——关键词打出来的分和向量算出来的相似度，不在一个尺度上。谁大谁小没有意义。而且两路都找到同一条内容时，怎么算？

**怎么做的。** 项目用了一套组合处理：

1. **两路各找各的**，各自给出候选。
2. **融合的时候比的是名次，不是分数**。这种做法只看"这条在两路里分别排第几"，避开分数尺度不一致的问题；同一条被两路都找到了，它的名次会被合并计算，**自然会往前提**。
3. **合并成一份候选**，同一份内容不会因为两路都命中而占两个位置。
4. **按剩余上下文位置裁剪**。这里算得挺细：先扣掉系统提示、这次对话已经用掉的部分、还要留给回答的空间，再留一点余量，**剩下的才是记忆能用的额度**，而且这个额度本身还有上限。

**位置真的不够时，它选择这次不交付**，而不是硬塞进去把对话挤坏。

:::tip 为什么不比较分数这件事值得单独提
“两路检索怎么融合”是 RAG 类项目的必答题。答"加权平均"很常见，但**加权平均要先解决分数尺度不一致**——而基于名次的融合直接绕开了这个问题，还顺带解决了"两路命中要加权"的需求。

这套思路（倒数排名融合）在搜索领域是成熟做法，能理解它为什么这么设计、什么时候该用它，比背下公式有用。
:::

## 亮点五：重复投递不会变成重复记忆

**要解决什么问题。** 客户端环境是不可靠的：网络会重试、进程会被杀、队列会补投。同一轮对话被送两三次，是**必然发生**的事。

如果处理不好，最直接的后果就是同一个规则在项目里存了三条，而且它们还会被认为"互相重复"，触发一轮多余的整理。

**难在哪。** 你要能区分两种"看起来一样"的情况：**同一轮因为重试被送了两遍**（要认出来，别重复记），和**内容真的冲突了**（要拒绝，因为这说明来源有问题）。这两种情况长得像，处理方式却完全相反。

**怎么做的。** 每一轮对话带自己的身份标识，服务端按它来判断：

| 情况 | 处理 |
| --- | --- |
| 同一轮、内容相同，重复投递 | 认得出来，返回同一份回执，不重复记 |
| 同一轮、内容不一致 | 判定为冲突并拒绝 |
| 版本顺序错乱 | 拒绝，要求按顺序投递 |
| 这一轮已经被删过 | 拒绝，不让它再进来 |

**而且整个接收过程落在一个事务里**：会话、轮次、正文、回执、后续任务要么全成、要么全不成。所以不会出现"对话存了但任务没排上"这种半截状态等你手工修。

:::info 幂等这件事的通用性
“重复请求会不会产生重复数据”是所有对外接口都要回答的问题。这里给的答案比较完整：**用业务身份去重、用内容指纹区分重试与冲突、用事务保证不半途而废、用墓碑挡住已删数据的复活。**

这四个手段各自解决一类问题，合起来才叫幂等。只做第一步是不够的。
:::

## 亮点六：两个人同时改，不会互相覆盖

**要解决什么问题。** 内容是可以被多方改动的：你在控制台改一条经验，同时某个 AI 工具里的一轮对话触发了自动整理，也可能同一个人在两个页面同时操作。

如果不管，就会出现**"我基于旧版本做的改动，把新版本冲掉了"**——而且这种事故很难发现，因为保存是成功的。

**难在哪。** 加锁当然可以，但会带来等待、超时、死锁一堆新问题；而且大部分时候根本没人抢，锁是白加的。

**怎么做的。** 项目统一用**乐观并发控制**：修改的时候带上"我看到的是哪一版"，服务端核对一下是不是还是那一版。不是就拒绝，让用户重新看一眼再改。

这套做法在项目里贯穿得很彻底——改记忆要核版本、审核建议要核对你看到的是哪一版、**连权限判断都带版本号**（权限关系变了就要求重新确认）。

实际用起来的体感是：偶尔看到一次"内容已被更新，请重新查看"，重看一眼再改。这点小麻烦换来的是不丢数据。

:::tip 为什么“贯穿得很彻底”比“用了什么技术”更重要
乐观并发控制是个很常见的技术，但**只在几个显眼的地方用它，别的地方还漏着**，等于没做。

而这里的做法是把它当成一条统一原则：**凡是"基于某个状态做的决定"，都要在真正执行时再核一遍这个状态有没有变。** 这条原则能推广到几乎任何系统。
:::

## 亮点七：上游一改，下游会重新整理——而且不会越跑越乱

**要解决什么问题。** 这是分层记忆带来的必然代价，也是我认为整个项目里最见功力的部分。

既然核心记忆是从场景归纳的、场景是从条目整理的、条目是从对话抽出来的，那么**底下任何一层变了，上面的结论就可能不再成立**：

- 那轮对话当时记错了，把原始对话**排除**掉。
- 某条规则**内容改了**。
- 一条过时的规则被**标记失效**。
- 某个会话整个**删掉**。

这四种情况下，上层结论的处境完全不同：内容变了要**重新归纳**；失效了要**停止使用**；来源全没了，上层的结论就**没有立足之地，得退场**。

不管这些，项目里会慢慢积累一批"来路不明的旧结论"，而且看起来都很正常——这是最危险的状态。

**难在哪。** 派生结果**不是按公式算出来的**，是模型生成的。这意味着两件事：跑两次结果可能不一样，所以不能靠"重算一下就好了"；而且模型调用要花钱，不能动不动就全量重跑。

**怎么做的。** 三个方面：

1. **按影响程度分级处理。** 内容改了 → 标成待更新，内容还能参考；失效了 → 停止交付；来源没了 → 直接退场。
2. **影响会一层层往上传。** 对话的变动影响条目，条目的变动影响场景，场景再影响核心。
3. **每一次重新处理都有身份。** 把受影响的层级、触发原因、涉及的来源、输入内容、规则版本都算进去——**同样的输入和原因只会有一次任务**，重跑不是重复劳动，也不会互相打架。

还有一点很实在：**给用户一个明确的闸门。** 自动触发的调整会自己跑，但"把历史内容按新规则全部重算"这种大规模操作**必须用户明确发起**，而且先给预览——要处理哪个层级、预计影响多少个版本，你看过再决定。这类操作一旦失控，跑的都是真金白银。

:::tip 这一条是整个项目里最值得深入的东西
“上游变了，下游派生数据怎么办”是数据系统的经典难题：搜索索引重建、离线数仓重跑、物化视图刷新，本质都是它。

而记忆系统里它更难，因为**派生结果不可复算**——模型每次生成的可能都不一样。所以必须靠"输入没变就不重跑"来保证稳定，而不是靠"重算就好了"。

能讲清楚这个取舍，是很扎实的工程理解。
:::

## 亮点八：使用资格和管理权是分开判断的

**要解决什么问题。** 团队场景下，最直觉的权限设计是"在团队里就能用团队的东西"。但这样会带出一个问题：**能用一个项目，是不是就等于能改它、能删它、能看别人在里面的聊天？**

**难在哪。** 权限判断越简单越好用，但越简单越容易越权。这两头总得选。

**怎么做的。** 项目把几件事拆成**独立判断**：

| 要判断的事 | 谁说了算 |
| --- | --- |
| 能不能用这个项目的经验 | 团队关系 + 项目的开放范围 + 项目是否处于可用状态 |
| 能不能管这个项目 | 只有负责人 |
| 能不能看原始对话 | 单独判断，按提交人过滤 |
| 能不能改某条内容 | 单独判断 |

拆开之后，每个请求要回答的问题就变得很具体：**这次操作需要哪一种权限，这个人有没有？** 而不是"他在团队里，那放行吧"。

**另外两条我特别想提：**

- **资格是每次都重新检查的。** 退出团队、账号被停用、项目被暂停、开放范围收回——之后的访问就会被拒，不需要等什么缓存过期。
- **查不清的时候往安全那边倒。** 权限信息暂时取不到时，按拒绝处理，而不是"先放行、事后再算"。

:::info 别把“用了权限框架”当成答案
权限这块真正的难点落在**边界划在哪里**，跟技术选型关系不大：哪些操作要单独授权、资格什么时候失效、异常情况往哪边倒。

这个项目把"使用"和"管理"拆开、把"看原始对话"再单独拆一层，这几个拆法本身就是设计判断。
:::

## 亮点九：一套服务适配多个 AI 客户端

**要解决什么问题。** 这个项目要给 Codex、Claude Code、OpenCode 提供记忆。但这三个工具的接入机制完全不同——有的用钩子，有的用插件，配置文件的格式和位置也各不相同。

**难在哪。** 装这个工具**会修改用户本机已有的配置文件**。这意味着一堆必须处理好的问题：装两次会不会变成两份？卸载会不会误删用户自己的东西？用户原来的配置会不会被搞坏？

**怎么做的。**

- **合并而不是覆盖。** 读出现有配置，只加自己需要的那部分，并且用自己的标记把新增内容圈起来。卸载时只删标记内的部分。
- **重复安装是安全的**，不会产生第二份配置。
- **卸载有明确边界**：只清自己写进去的，用户自己的配置一律不动。
- **互相冲突能被发现**，会提示而不是硬写。
- **多个客户端可以共存**：同一个目录装了几个客户端，卸载其中一个时，**项目绑定和个人凭据会保留**（因为其他客户端还在用）。

**还有版本问题。** AI 客户端更新很快。项目没有假装"支持所有版本"，而是把验证过的版本写清楚，同时**允许其他版本继续尝试**并如实记录真实版本号。这样做避免了最糟的情况——**客户端小版本升级之后功能悄悄失效，用户以为在记、实际什么都没记**。

:::tip “改别人的配置文件”是个被低估的活儿
CLI 工具、代码生成器、脚手架、IDE 插件都会碰到这个问题。这里给出的是一套可复用的思路：**标记化写入、幂等安装、限定范围的卸载、冲突检测**。

面试里讲这个，比说"支持三个客户端"具体得多。
:::

## 亮点十：服务出问题，不耽误用户自己的活

**要解决什么问题。** 这是个辅助服务。如果它挂了就导致用户写不了代码，那它就是个负资产。

**怎么做的。** 项目在多处体现了同一个取向：**不挡在用户的工作流中间。**

- **取经验失败** → 这轮对话照常进行，只是不带项目经验，并且明确告诉你这次没注入。
- **存对话失败** → 内容先在你本机排队，等服务恢复再投递。
- **本机队列也不是无限的** → 大小、条数、保留天数都有上限。超了就明确拒绝并计入统计，而不是悄悄堆到把磁盘撑满。
- **进程被杀、断电** → 队列里每条内容带租约标记，过期的租约会被自动放回待投递队列，不会卡死。

**形式：分层结构图。** 从下往上画：最底层是"采集与幂等接收"，往上是"模型提取与去重（结构化校验 + 用途绑定）"，再往上是"分层演化与来源治理（版本、谱系、协调、重算）"，最上面是"召回与交付（两路融合 + 预算控制）"。左侧竖着一条"贯穿全部：乐观并发 + 版本核对"，右侧竖着一条"贯穿全部：权限与多租户隔离"。

## 还有几个没展开但值得一提的

上面十条是主线，另外这几处也做得挺细，我列一下，你可以顺着往下看：

| 做了什么 | 为什么值得一提 |
| --- | --- |
| 采集只认可靠的完成信号 | 不同客户端用什么信号表示"这轮答完了"是不一样的，要分别处理，否则会收到半截对话 |
| 交付时重新核对版本 | 查找和交付之间有时间差，这期间内容可能被改，交出去前再核一遍，避免把作废的结论给出去 |
| 处理任务有租约和续约 | 任务执行时定期续约，进程挂了之后过期的任务能被重新拾起，不会永远卡在"执行中" |
| 处理失败区分可重试和不可重试 | 模型超时可以重试，配置错了重试也没用——分开处理，避免无意义的重跑 |
| 导入导出带校验和 | 导出的包带内容完整性校验，导入时核对，避免文件损坏后被当成正常内容导进去 |
| 资源有明确上限 | 一个项目能关联的记忆库数量、一次能返回的候选数量、工具调用次数都有上限，超出会有明确提示 |
