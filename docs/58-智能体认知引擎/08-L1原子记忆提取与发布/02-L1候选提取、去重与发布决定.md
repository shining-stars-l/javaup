# L1候选提取、去重与发布决定

## 从 Lease 到四种决定

这一篇接着上一篇的 `L1EvolutionProcessing.process()`。worker 已经拿到合法 Lease，接下来按固定顺序执行：

1. 从 `evolution_job_input_message` 回读这一批 L0，确认消息仍然存在、仍是 `CAPTURED` 且交互已成功。
2. 把 ASSISTANT 消息关联的可信召回版本一起读出来。助手如果只是复述召回内容，提取输入会遮住这段回复正文。
3. 调用 `L1_EXTRACT` 模型，把对话整理成事实、偏好、约束、事件候选。
4. 校验候选必须非空、key 唯一、来源只能来自本 Job 的消息。
5. 读取当前仍为 `ACTIVE` 的 L1 Atom 和当前版本。
6. 调用 `L1_DEDUP` 模型，给每个候选安排 `STORE`、`UPDATE`、`MERGE` 或 `SKIP`。
7. 后端再做一轮硬校验，把候选和决定拼成发布输入；模型输出不会直接写数据库。
