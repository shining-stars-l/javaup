# 来源失效后怎样协调L2与L3

## 先看这条流程从哪儿开始

小伙伴可以先把“协调”理解成一件具体的事：某条 L1 或 L2 来源变了，后端沿着高层记忆的**当前版本谱系**找出受影响的目标，再决定它还能不能交付、要不要重算。这里的“来源”是记忆版本，不是前端页面提交的一段文本。

目前生产代码里，我查到两个实际调用点。外部会话的轮次被排除、删除，或整个会话被删除时，`JdbcExternalConversationGovernance.invalidate()` 先使派生 L1 失效，再用该 L1 的旧版本触发协调。人工维护 L2 时，`JdbcHighLevelManualGovernance.change()` 用修改前的 L2 版本触发 L3 协调。`LOWER_LEVEL_CHANGED` 的普通变化策略已经实现并有测试，但当前生产调用点没有发出这个触发类型，所以别把它理解成“每次 L1 更新都会自动调用协调器”。
