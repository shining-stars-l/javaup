# L1任务租约、心跳与过期恢复

## 我们先看后台任务怎样继续跑下去

这一组文档按三个部分讲解后台处理任务：先看 L1 的租约、心跳和过期恢复，再看负责人发起的重试与取消，最后看 L2/L3 的提交检查、进程关闭和服务健康。每篇都顺着对应请求的调用顺序展开源码。

采集数据后，L1 整理任务已经保存在数据库里。后台线程再去领取任务、调用处理器、提交结果。假如模型还在响应，应用突然退出，数据库里那条 `RUNNING` 任务就需要有人处理，否则后续整理会一直等它。

我把这段后端流程按一次轮询的顺序展开：启动线程 → 回收过期任务 → 登记到期资产 → 领取一个 Job → 独立心跳续租 → 结束 Attempt。L1 内容怎样提取属于处理器的职责，这里重点看它运行期间谁能写状态、失败后从哪里继续。

| 数据 | 保存内容 | 讲解时要区分的地方 |
| --- | --- | --- |
| `evolution_job` | 冻结的输入、业务状态、Job revision | 人工重试要比较这个 revision |
| `evolution_job_runtime` | 到期时间、活动租约、token、state revision | 心跳也会更新运行状态，Job revision 可以不变 |
| `evolution_job_attempt` | 每次尝试的编号、起止时间、失败码 | 重试追加 Attempt，保留以前的失败 |
| `l1_success_cursor` | 上次成功处理到的来源位置 | 失败和回收都保留原成功位置 |

当前默认租约是 **60 秒**，心跳间隔是 **15 秒**。这些数字分别来自执行策略和运行时类中的常量。
