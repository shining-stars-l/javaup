## 从业务角度看这个项目解决了什么问题
### 购票助手：把客服从重复劳动中解放出来
做购票系统的人都知道，用户最爱问的问题就那么几类：

+ "这个演唱会还有票吗？"
+ "最便宜的票多少钱？"
+ "怎么退票？"
+ "一个账号能买几张？"

这些问题的答案要么在数据库里，要么在规则文档里，答案是确定的。但每天就是有无数人问同样的问题，客服得一遍遍回答。高峰期的时候，比如热门演唱会开票前几天，客服忙得焦头烂额，用户等半天也等不到回复。

有了购票助手之后，这些重复问题AI可以秒回。用户不用排队等人工客服，体验好了；客服不用处理这些简单问题，可以专注处理复杂情况。

实际使用下来，大部分日常咨询AI都能处理，只有涉及到退款纠纷、异常订单这种需要人工判断的才转给客服。

### 运维助手：把排查故障的时间从分钟级缩短到秒级
运维同学排查问题的流程，以前是这样的：

1. 看到告警消息
2. 登录日志平台，搜索相关日志
3. 登录监控平台，查看指标曲线
4. 如果是分布式问题，还要用traceId去追踪调用链路
5. 综合分析，定位问题

这一套下来，顺利的话十几分钟，不顺利的话可能要半小时。而且如果是夜里值班，人困了操作更慢，还容易遗漏关键信息。

有了运维助手之后：

+ 直接问"帮我查一下order-service最近的错误日志"，它去ES里查
+ 直接问"这个traceId走了哪些服务"，它帮你追踪链路
+ 直接问"user-service的JVM内存情况怎么样"，它去Prometheus查指标

省去了在多个系统之间切换的时间，也不用记住每个平台怎么操作。问就是了，AI帮你查。

而且AI不会累、不会困，夜里凌晨三点的告警它也能秒响应。

### 规则助手：让文档真正被用起来
很多团队都有这个问题：文档写了一堆，但没人看。

我们的规则文档也是这样。订票规则、退票政策、常见问题FAQ，写得很详细，但用户就是不看。问客服是第一反应，哪怕文档里明明白白写着答案。

规则助手用RAG技术，把文档变成了可以对话的知识库。用户问"演唱会能不能退票"，它从文档里找到相关内容，组织成通顺的回答返回给用户。

用户不用自己翻文档了，问就行了；文档内容也真正发挥了价值，不再是"写了没人看"的摆设。

## 从技术角度看这个项目有什么亮点
### Function Call：让AI能真正干活
普通的聊天机器人只能动嘴，不能动手。你让它帮你查东西，它只能告诉你"你可以去这里查"，不能真的帮你查。

我们的购票助手不一样。用户说"帮我查一下北京有什么演唱会"，它真的会调用后端接口，从数据库里把演唱会列表查出来，整理成好看的格式告诉用户。

这是通过Function Call实现的。我们给大模型定义了一系列工具函数：

```java
@Tool(description = "根据地区或者类型查询推荐的节目")
public List<ProgramSearchVo> selectProgramRecommendList(ProgramRecommendFunctionDto dto) {
    return programCall.recommendList(dto);
}

@Tool(description = "生成用户购买节目的订单，返回订单号")
public CreateOrderVo createOrder(CreateOrderFunctionDto dto) {
    // 查节目、验证用户、创建订单...
}
```

大模型会根据用户的意图，自动判断需要调用哪个函数、传什么参数。整个过程是智能的，不是硬编码的if-else。

用户说"我想买周杰伦演唱会的票"，大模型会先调用查询函数找到节目，然后一步步收集用户信息，最后调用下单函数创建订单。整个流程是AI自己规划和执行的。

### RAG：让大模型说话有据可依
大模型有个臭毛病：不知道的事情也敢瞎说。你问它大麦的退票政策是什么，它可能编一个看起来很像真的答案出来。这在商业系统里是不能接受的。

我们用RAG解决这个问题。把规则文档向量化存起来，用户提问的时候先检索相关内容，把检索到的内容塞给大模型，让它基于这些真实的信息来回答。

关键配置：

+ topK=8：检索最相关的8个文档片段
+ similarityThreshold=0.3：过滤掉相关性太低的结果
+ prompt约束："如果找不到相关信息，不要编造"

这样大模型就只会说它"看到"的内容，不会瞎编了。

### MCP：把工具做成可插拔的服务
运维工具的实现比较复杂，涉及到ES查询、Prometheus查询，而且这些工具以后可能还会扩展。如果直接写在主服务里，会让代码变得很臃肿。

我们把工具抽出来，做成独立的MCP服务：

+ damai-mcp-log-service：所有日志相关的工具
+ damai-mcp-metrics-service：所有监控指标相关的工具

主服务通过MCP协议调用这些工具服务。好处是：

1. **解耦**：工具服务可以独立开发、独立部署、独立扩展
2. **复用**：同一套工具可以被多个AI服务调用
3. **标准化**：MCP是业界标准协议，以后换框架也能用

### SSE流式输出：提升用户体验
大模型生成回答需要时间，尤其是长回答可能要好几秒。如果让用户干等着，体验很差。

我们用SSE（Server-Sent Events）实现流式输出。大模型生成一个字，就推送一个字到前端。用户能看到文字像打字一样一个个蹦出来，感觉AI在"实时思考"，而不是在发呆。

前端用Flux来处理流式数据：

```java
@RequestMapping(value = "/chat", produces = "text/html;charset=utf-8")
public Flux<String> chat(@RequestParam("prompt") String prompt,
                         @RequestParam("chatId") String chatId) {
    return assistantChatClient.prompt()
            .user(prompt)
            .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, chatId))
            .stream()
            .content();
}
```

### 多轮对话记忆：让AI记住上下文
单轮对话的AI是"金鱼脑"，每次都是从头开始。用户说"有没有便宜点的"，AI不知道用户说的是什么东西的便宜点。

我们用MessageWindowChatMemory管理对话历史：

```java
@Bean
public ChatMemory chatMemory(ChatMemoryRepository chatMemoryRepository) {
    return MessageWindowChatMemory.builder()
            .chatMemoryRepository(chatMemoryRepository)
            .maxMessages(20)
            .build();
}
```

最多保留20轮对话，超出的部分会被清理掉（也可以做总结后存储）。每次对话都带上历史消息，大模型就能理解上下文了。

## 这个项目体现了什么能力
### 技术选型能力
这个项目涉及到很多技术选型：

+ 为什么用Spring AI而不是LangChain？——Java技术栈、强类型、生产稳定性
+ 为什么用DeepSeek和通义千问？——国内模型、性价比高、合规
+ 为什么用SSE而不是WebSocket？——单向推送场景，SSE更简单
+ 为什么用MCP协议？——标准化、可复用、可扩展

每个选择都有理由，不是随便拍脑袋的。面试的时候能把这些理由讲清楚，说明你对技术有思考，不是只会照着文档抄。

### 架构设计能力
项目的架构设计也有讲究：

+ 主服务和MCP工具服务分离，职责清晰
+ 多个ChatClient分别处理不同场景（购票、运维、规则问答）
+ Advisor链式设计，每个Advisor负责一个切面（历史记录、标题生成、消息记忆）

这种设计让代码好维护、好扩展。加新功能不用改老代码，加新工具不用动主服务。

### 问题解决能力
做这个项目的过程中遇到了很多问题：

+ RAG检索效果不好→调整分块策略和topK参数
+ 大模型回答不准确→优化prompt、加约束条件
+ 用户体验不好→用SSE实现流式输出
+ 工具服务耦合严重→抽出来做MCP服务

每个问题都有对应的解决方案，面试的时候讲这些解决问题的过程，比直接说"我用了什么技术"更有说服力。

### 业务理解能力
做AI项目不是纯技术活，得理解业务场景。

购票助手要知道用户的购票流程是什么、哪些信息是必须收集的、哪些规则是不能违反的。运维助手要知道排查故障的思路是什么、需要看哪些日志和指标。

这些业务理解体现在prompt的设计上。我们的prompt不是泛泛的"你是一个助手"，而是把具体的业务流程和规则都写进去了，让AI知道每一步该怎么做。

## 面试时怎么讲这些亮点
讲亮点不要堆砌技术名词，要讲故事。

**讲背景**：为什么要做这个？解决什么问题？

> "购票系统每天要处理大量重复咨询，客服忙不过来；运维排查故障要在好几个系统之间切换，效率很低。"
>

**讲方案**：你是怎么解决的？

> "我们做了AI助手，购票助手用Function Call调用业务接口，运维助手用MCP工具查日志和监控，规则助手用RAG检索知识库。"
>

**讲挑战**：过程中遇到了什么问题？怎么解决的？

> "RAG检索效果一开始不好，调了很多参数，还优化了文档的格式和分块策略。"
>

**讲效果**：最终达到了什么效果？

> "购票助手能处理大部分日常咨询，运维助手把故障排查时间缩短到一两分钟。"
>

这样讲出来，面试官能感受到你是真的做过这个项目、真的思考过这些问题，而不是背书背出来的。
