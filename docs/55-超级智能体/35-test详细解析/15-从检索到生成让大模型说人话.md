# 从检索到生成：让大模型说人话

## 检索到了对的内容，不等于能给出对的答案

前面几篇把检索链路讲透了——问题改写、混合检索、重排序，一路下来能拿到高质量的Top-K候选内容。很多人到这一步就觉得大功告成了。

但实际跑起来，你会发现一个扎心的事实：**好内容 + 烂Prompt = 烂答案**。

来看几个真实的翻车场景。

**翻车一：用自己的常识覆盖检索结果**

用户问：我们公司的年假是怎么规定的？

检索到的内容：本公司员工入职满一年后享有10天年假，满五年后享有15天年假。

模型回答：根据国家规定，员工工作满1年不满10年的，年休假5天；满10年不满20年的，年休假10天...

检索内容明明说的是"10天"和"15天"，模型却用国家法定标准覆盖了公司的自定义规定。

**翻车二：在检索内容基础上"合理补充"**

用户问：退货运费谁承担？

检索到的内容：质量问题退货，运费由商家承担。

模型回答：质量问题退货，运费由商家承担，退款将在3-5个工作日内原路返回。

"3-5个工作日原路返回"这个信息检索内容里完全没有，是模型根据电商行业的通用经验自己编的。如果实际退款周期是7-15天，用户就会投诉。

**翻车三：把不同文档的信息混在一起**

检索返回了两个文档块：
- 块1：基础版套餐月费99元，包含100GB流量
- 块2：尊享版套餐月费199元，包含无限流量和国际漫游

模型回答：基础版套餐月费99元，包含无限流量。

模型把块2的"无限流量"安到了块1的"基础版"上，生成了一个看起来对但实际上错的答案。

## RAG Prompt的三段式结构

RAG场景下的Prompt由三段组成，各司其职：

1. **系统指令（System Prompt）**：定义模型的角色和行为边界
2. **检索上下文（Retrieved Context）**：把检索到的Top-K内容喂给模型
3. **用户问题（User Query）**：用户的原始提问

### 系统指令：给模型画红线

系统指令是整个Prompt的总纲，最核心的任务是：**让模型只基于检索内容回答，不要用自己的知识自由发挥**。

一个可以直接用的模板：

```
你是一名专业的客服助手。你的任务是根据【参考资料】中的信息，
准确回答用户的问题。

请严格遵守以下规则：
1. 只基于【参考资料】中的内容回答问题，不要使用你自己的知识。
2. 如果【参考资料】中没有足够的信息，请明确回答：
   "根据现有资料，暂时无法回答该问题。建议您联系人工客服。"
3. 不要编造任何【参考资料】中没有提到的信息，
   包括数字、日期、金额等具体细节。
4. 回答时请引用参考资料的编号，格式为[1]、[2]等。
5. 如果多条参考资料的信息存在冲突，
   请指出冲突并告知用户以最新的资料为准。
6. 用简洁、友好的语气回答。
```

每条规则解决一个具体问题：

| 规则 | 解决的问题 |
| :--- | :--- |
| 只基于参考资料回答 | 防止模型用训练知识覆盖检索结果 |
| 信息不足时明确告知 | 给模型一个"兜底出口"，不知道就说不知道 |
| 不要编造具体细节 | 数字、日期、金额是幻觉重灾区 |
| 引用参考资料编号 | 让答案可追溯，用户能验证 |
| 处理信息冲突 | 多个文档块说法不一致时不要自己选一个 |
| 语气要求 | 控制回答风格 |

:::caution System Prompt的常见误区
**太短没约束**："你是客服助手，请回答问题。"——等于没有约束，模型会自由发挥。
**太长指令冲突**：写了几十条规则，互相矛盾。经验法则是5-8条核心规则。
**没有兜底指令**：不告诉模型"不知道怎么办"，它会默认"尽力回答"，也就是开始编造。
:::

### 检索上下文：带编号、带来源

推荐的格式是每个文档块带编号、带来源信息，用明确的分隔符隔开：

```
【参考资料】

[1] 来源：退货政策文档 | 更新时间：2026-01-15
本公司产品拆封后不支持七天无理由退货。
如需退货，需经售后检测确认存在质量问题。

[2] 来源：通用退货规则 | 更新时间：2026-01-10
标准商品在签收后7天内可申请无理由退货，
商品需保持完好，不影响二次销售。

[3] 来源：退货运费规则 | 更新时间：2026-02-01
质量问题退货，运费由商家承担；
非质量问题退货，运费由买家承担。
```

设计要点：
- **编号[1][2][3]**：方便模型引用，也方便后端解析
- **来源信息**：告诉模型和用户这条信息从哪来的
- **更新时间**：信息冲突时，模型可以根据时间判断哪条更新
- **明确分隔**：避免模型把相邻块的内容混在一起理解

### 上下文窗口的限制

虽然现在很多模型支持128K甚至更长的上下文，但塞太多内容进去并不好：

- **关键信息被稀释**：内容越多，噪音越大，模型越容易被不相关的内容干扰
- **迷失在中间（Lost in the Middle）**：研究表明，大模型对上下文中间位置的信息关注度较低
- **成本增加**：输入token越多，API费用越高

经验值：简单事实问答给3-5个块，复杂对比问题给5-8个块。如果用了Reranker，Top-K质量已经很高，3-5个就够了。

## 幻觉抑制：让模型不知道就说不知道

### 幻觉的三种典型表现

**篡改事实**：检索内容说A，模型回答B。模型用自己的常识覆盖了检索到的具体规则。

**凭空捏造**：检索内容里没有某个信息，模型自己补了一个。数字、日期、金额是重灾区。

**张冠李戴**：把文档块A的信息安到文档块B的主体上。每个单独的信息点都对，但组合方式是错的。

### 五个实用的抑制技巧

**技巧一：反复强调知识来源限制**

```
只基于【参考资料】中的内容回答问题，不要使用你自己的知识。
```

没有这条指令时，模型把检索内容当"参考"；有了这条，模型把检索内容当"唯一依据"。

**技巧二：给兜底出口**

```
如果【参考资料】中没有足够的信息，请明确回答：
"根据现有资料，暂时无法回答该问题。"
```

不给这个出口，模型会默认"尽力回答"——也就是开始编造。

**技巧三：禁止编造具体细节**

```
不要编造任何【参考资料】中没有提到的信息，
包括数字、日期、金额等具体细节。
```

**技巧四：要求先引用再回答**

让模型标注引用来源，间接抑制幻觉——因为模型需要为每句话找到对应的文档块，找不到就不敢说。

**技巧五：降低Temperature参数**

Temperature控制模型输出的随机程度：
- Temperature = 0：几乎总是选择概率最高的词，输出最确定
- Temperature = 0.7：默认值，有一定随机性
- Temperature = 1.0+：输出非常随机

RAG场景推荐Temperature设为0~0.3。不设0是因为完全确定性的输出有时候会过于生硬，0.1保留了一点灵活性，同时几乎不会产生幻觉。

### 兜底回答的设计

直接回答"我不知道"会让用户觉得系统没用。好的兜底回答应该：

**完全无法回答时**：
```
根据现有资料，暂时无法回答该问题。
建议您联系人工客服获取更多帮助。
```

**部分可以回答时**：
```
关于退货运费，商家承担质量问题的运费[1]。
但关于退款到账时间，现有资料中没有说明，
建议您联系人工客服确认。
```

**问题超出范围时**：
```
这个问题超出了我的服务范围。
我主要负责解答售后相关问题，
如果您有退换货、物流等方面的疑问，随时可以问我。
```

## 引用对齐：让答案可追溯

### 为什么需要引用

用户看到一个回答，心里的第一反应是"这个答案靠谱吗"。如果模型能标注"这段话来自《退货政策》第3条"，用户就能自己去验证。

在企业级RAG系统中，引用对齐更是刚需：
- 金融、医疗、法律等行业，回答必须有据可查
- 出了问题能追溯到具体的知识来源
- 用户能看到答案的依据，逐步建立对系统的信任

### 引用解析的Java实现

模型输出的是带`[1]`、`[2]`标记的纯文本，后端需要解析这些标记，关联到对应的文档块元数据。

```java
public class CitationParser {

    /** 从模型回答中提取所有引用编号 */
    public static Set<Integer> extractCitations(String answer) {
        Set<Integer> citations = new TreeSet<>();
        Pattern pattern = Pattern.compile("\\[(\\d+)]");
        Matcher matcher = pattern.matcher(answer);
        while (matcher.find()) {
            citations.add(Integer.parseInt(matcher.group(1)));
        }
        return citations;
    }

    /** 将引用编号替换为可点击的链接 */
    public static String renderCitations(String answer,
            Map<Integer, ChunkMeta> metaMap) {
        Pattern pattern = Pattern.compile("\\[(\\d+)]");
        Matcher matcher = pattern.matcher(answer);
        StringBuilder result = new StringBuilder();
        while (matcher.find()) {
            int index = Integer.parseInt(matcher.group(1));
            ChunkMeta meta = metaMap.get(index);
            if (meta != null) {
                String link = String.format(
                    "<a href=\"%s\" title=\"%s\">[%d]</a>",
                    meta.sourceUrl(), meta.source(), index);
                matcher.appendReplacement(result, link);
            }
        }
        matcher.appendTail(result);
        return result.toString();
    }
}
```

## 完整的RAG生成链路：Java实战

把检索、上下文组装、大模型调用、引用解析串成一个完整的流程。

### 数据结构定义

```java
/** 检索到的文档块 */
@Getter
@AllArgsConstructor
public class RetrievedChunk {
    private String content;      // 文本内容
    private String source;       // 来源文档名
    private String sourceUrl;    // 原文链接
    private String updateTime;   // 更新时间
    private Double score;        // 重排序得分
}

/** RAG生成结果 */
@Data
public class RAGResponse {
    private String answer;                    // 原始回答（带[1][2]标记）
    private String renderedAnswer;            // 渲染后的回答
    private List<CitationInfo> citations;     // 引用详情

    @Data
    public static class CitationInfo {
        private Integer index;
        private String source;
        private String sourceUrl;
        private String chunkContent;
    }
}
```

### 核心生成服务

```java
public class RAGGenerationService {

    private static final String API_URL =
        "https://api.siliconflow.cn/v1/chat/completions";
    private static final String API_KEY = "你的API Key";
    private static final String MODEL = "Qwen/Qwen2.5-7B-Instruct";

    private static final OkHttpClient client = new OkHttpClient.Builder()
            .connectTimeout(30, TimeUnit.SECONDS)
            .readTimeout(60, TimeUnit.SECONDS)
            .build();
    private static final Gson gson = new Gson();

    private static final String SYSTEM_PROMPT = """
        你是一名专业的客服助手。
        根据【参考资料】中的信息，准确回答用户的问题。

        【回答规则】
        1. 只基于【参考资料】回答，不要使用你自己的知识。
        2. 信息不足时明确告知用户，并建议联系人工客服。
        3. 不要编造参考资料中没有的信息。
        4. 多条资料冲突时，指出冲突并以最新资料为准。

        【引用规则】
        - 回答时引用参考资料编号，格式为[1]、[2]等。
        - 只引用实际使用到的参考资料。

        【格式要求】
        - 简洁友好，覆盖核心要点，不展开无关背景。
        """;

    /** 组装带编号的上下文 */
    public String buildContext(List<RetrievedChunk> chunks) {
        StringBuilder ctx = new StringBuilder("【参考资料】\n\n");
        for (int i = 0; i < chunks.size(); i++) {
            RetrievedChunk c = chunks.get(i);
            ctx.append(String.format("[%d] 来源：%s | 更新时间：%s\n",
                    i + 1, c.getSource(), c.getUpdateTime()));
            ctx.append(c.getContent()).append("\n\n");
        }
        return ctx.toString();
    }

    /** 调用大模型Chat API */
    public String callLlm(String systemPrompt,
            String context, String userQuery) throws IOException {
        String userMessage = context + "【用户问题】\n" + userQuery;

        JsonObject body = new JsonObject();
        body.addProperty("model", MODEL);
        body.addProperty("temperature", 0.1);
        body.addProperty("max_tokens", 1024);

        JsonArray messages = new JsonArray();

        JsonObject sysMsg = new JsonObject();
        sysMsg.addProperty("role", "system");
        sysMsg.addProperty("content", systemPrompt);
        messages.add(sysMsg);

        JsonObject userMsg = new JsonObject();
        userMsg.addProperty("role", "user");
        userMsg.addProperty("content", userMessage);
        messages.add(userMsg);

        body.add("messages", messages);

        Request request = new Request.Builder()
                .url(API_URL)
                .addHeader("Authorization", "Bearer " + API_KEY)
                .post(RequestBody.create(
                    gson.toJson(body),
                    MediaType.parse("application/json")))
                .build();

        try (Response response = client.newCall(request).execute()) {
            JsonObject json = gson.fromJson(
                response.body().string(), JsonObject.class);
            return json.getAsJsonArray("choices")
                    .get(0).getAsJsonObject()
                    .getAsJsonObject("message")
                    .get("content").getAsString();
        }
    }

    /** 解析引用编号 */
    public List<RAGResponse.CitationInfo> parseCitations(
            String answer, List<RetrievedChunk> chunks) {
        Set<Integer> cited = new TreeSet<>();
        Matcher m = Pattern.compile("\\[(\\d+)]").matcher(answer);
        while (m.find()) cited.add(Integer.parseInt(m.group(1)));

        List<RAGResponse.CitationInfo> list = new ArrayList<>();
        for (int idx : cited) {
            if (idx >= 1 && idx <= chunks.size()) {
                RetrievedChunk c = chunks.get(idx - 1);
                RAGResponse.CitationInfo info = new RAGResponse.CitationInfo();
                info.setIndex(idx);
                info.setSource(c.getSource());
                info.setSourceUrl(c.getSourceUrl());
                info.setChunkContent(c.getContent());
                list.add(info);
            }
        }
        return list;
    }

    /** 完整的RAG生成流程 */
    public RAGResponse generate(List<RetrievedChunk> chunks,
            String userQuery) throws IOException {
        String context = buildContext(chunks);
        String answer = callLlm(SYSTEM_PROMPT, context, userQuery);
        List<RAGResponse.CitationInfo> citations =
            parseCitations(answer, chunks);

        RAGResponse resp = new RAGResponse();
        resp.setAnswer(answer);
        resp.setCitations(citations);
        return resp;
    }
}
```

几个设计要点：
- System Prompt和上下文分开传递——system放在`role: system`，上下文放在`role: user`，模型能更清楚地区分"行为指令"和"参考内容"
- Temperature设为0.1——不设0是因为完全确定性的输出有时候过于生硬
- 引用解析做了边界检查——防止模型输出不存在的引用编号

## Prompt迭代优化：用bad case驱动

Prompt不是写一版就完事的。上线后会不断收到bad case，需要持续调优。

### 迭代流程

**第一步：收集bad case**

记录三个信息：用户问题、检索到的文档块、模型的错误回答。

**第二步：分类归因**

| 类别 | 判断标准 | 优化方向 |
| :--- | :--- | :--- |
| 篡改事实 | 文档说A，模型说B | 强化"只基于参考资料"的指令 |
| 凭空捏造 | 模型补充了文档里没有的细节 | 强化"不要编造"，特别是数字日期 |
| 张冠李戴 | 混淆了不同文档块的信息 | 要求逐条引用，不合并不同来源 |
| 答非所问 | 回答了相关但不对口的内容 | 强化"聚焦用户问题"的指令 |
| 超出边界 | 回答了知识库范围外的问题 | 强化边界约束 |

**第三步：针对性修改Prompt**

举个例子。如果发现模型经常把不同文档块的数字混在一起，就在规则中增加：

```
引用不同参考资料的信息时，请明确区分各条资料的适用条件，
不要将不同资料的信息合并表述。
```

:::tip Prompt调优是持续过程
建议建立一个bad case库，每次修改Prompt后，用所有历史bad case回归测试，确保修了新问题没有引入老问题。Prompt调优没有终点，只有不断逼近的最优解。
:::

## 答案约束：控制输出的格式和边界

### 格式约束

**JSON格式（API接口场景）**：

```
请以JSON格式回答，包含以下字段：
- answer：回答内容
- citations：引用的参考资料编号列表
- confidence：确信程度（high/medium/low）
```

**列表格式（知识卡片场景）**：

```
请用编号列表的格式回答，每条信息独立成行。
```

### 边界约束

用户不一定只问知识库范围内的问题。如果不做边界约束，模型会用自己的知识回答——这不仅偏离了系统定位，还可能产生不当言论。

```
你只负责回答与售后、退换货、物流配送相关的问题。
如果用户的问题超出这个范围，请礼貌地告知用户。
不要回答涉及品牌对比、价格预测、个人观点等主观性问题。
```

### 生产级System Prompt模板

把所有约束整合在一起：

```
你是一名专业的客服助手。

【角色与边界】
- 只负责回答与售后、退换货、物流配送相关的问题。
- 超出范围的问题，礼貌告知并引导回售后话题。
- 不回答品牌对比、价格预测等主观性问题。

【回答规则】
1. 只基于【参考资料】回答，不使用自己的知识。
2. 信息不足时明确告知，并建议联系人工客服。
3. 不编造参考资料中没有的信息。
4. 多条资料冲突时，指出冲突并以最新资料为准。
5. 不同资料的信息不要合并表述，明确区分适用条件。

【引用规则】
- 引用参考资料编号，格式为[1]、[2]等。
- 只引用实际使用到的参考资料。

【格式要求】
- 简洁友好，覆盖核心要点。
- 不展开与问题无关的背景知识。
```

分组结构（角色与边界、回答规则、引用规则、格式要求）让模型更容易理解每条指令的优先级，也方便你后续针对某个维度做调优。

## 小结

RAG的生成阶段是整个系统的"最后一公里"：

- **三段式Prompt**是基础：System Prompt定义行为边界，检索上下文提供事实依据，用户问题明确回答目标
- **幻觉抑制**是底线：通过限定知识来源、兜底指令、禁止编造、要求引用、低Temperature，把模型的自由发挥空间压到最小
- **引用对齐**是信任基石：文档块带编号 + Prompt要求引用 + 后端解析引用标记
- **答案约束**是业务适配：格式、长度、边界根据场景灵活控制

一句话总结：检索决定了答案的上限（能不能找到对的信息），生成决定了答案的下限（找到了对的信息能不能说对）。
