# 让检索更聪明：问题改写四板斧

## 你说的和知识库说的，不是一回事

做过RAG系统的同学应该都有这种体验：明明知识库里有答案，但用户一问就是检索不到。

为什么？因为用户说话的方式和知识库存储的方式之间，存在一条巨大的鸿沟。

来看几个真实场景：

**场景一：口语化表达**

用户问："那个K8s的pod老是挂怎么搞"

知识库里存的是："Kubernetes Pod CrashLoopBackOff 故障排查指南"

两者说的是同一件事，但向量检索可能匹配不上——"老是挂"和"CrashLoopBackOff"在语义空间里的距离可能比你想象的远。

**场景二：多轮对话中的指代**

```
第一轮：Redis的持久化机制有哪些？
第二轮：它们的区别是什么？  ← "它们"指什么？
```

"它们的区别是什么"这几个字单独拿去检索，能检索到什么？大概率是一堆不相关的对比文档。

**场景三：一个问题藏着好几个问题**

"Spring Cloud Gateway和Nginx有什么区别，我们的微服务网关应该选哪个"

这其实是三个问题：Gateway的特点、Nginx的特点、选型建议。一次检索很难同时覆盖。

:::info 问题改写的本质
问题改写（Query Rewriting）是RAG检索前的预处理环节，核心目标是弥合"用户表达习惯"和"知识库存储方式"之间的差距。它不改变用户的意图，只是把意图翻译成更适合检索的形式。
:::

## 四种改写策略

### 策略一：富化——把残缺的问题补完整

**适用场景**：多轮对话中的指代消解、口语化表达、信息缺失。

用户在聊天过程中经常会省略主语、用代词替代前文提到的实体。比如先聊了Redis，接着问"它支持事务吗"——这个"它"如果不还原成"Redis"，检索就会跑偏。

富化的做法是：把对话历史和当前问题一起交给大模型，让它输出一个独立完整的新问题。

**举个例子**

```
对话历史：
  用户：RocketMQ的消息堆积怎么处理？
  助手：可以通过增加消费者数量、调整消费线程池大小...

当前问题：那它和Kafka比呢？

富化后：RocketMQ和Kafka在消息堆积处理能力方面有什么区别？
```

**Prompt模板**

```
你是一个问题重写优化器。

根据下面的对话历史和用户当前问题，重写为一个独立、完整、
包含所有必要背景信息的新问题，用于知识库检索。

对话历史：
{CHAT_HISTORY}

当前问题：
{QUESTION}

直接输出重写后的问题，不要解释。
```

### 策略二：分解——把大象装进冰箱分几步

**适用场景**：复合问题、多跳推理问题。

有些问题看起来是一个问题，实际上需要分步回答。直接拿去检索，很难一次命中所有需要的信息。

**多跳问题的例子**

```
原始问题：Spring Boot 3.x默认使用的日志框架是什么，它的异步日志怎么配置？

分解后：
1. Spring Boot 3.x默认使用哪个日志框架？
2. Logback的异步日志配置方式是什么？
```

第一个子问题检索到"Spring Boot 3.x默认使用Logback"，第二个子问题才能精准检索到Logback的异步配置方法。如果不分解，直接检索原始问题，可能返回一堆Spring Boot配置的通用文档，但不一定包含异步日志的具体配置。

**对比问题的例子**

```
原始问题：MyBatis和MyBatis-Plus有什么区别，项目里该用哪个？

分解后：
1. MyBatis的核心特性和适用场景
2. MyBatis-Plus相比MyBatis增加了哪些功能
3. MyBatis和MyBatis-Plus的选型建议
```

**Prompt模板**

```
你是一名查询逻辑分析专家。

将用户的复杂问题分解为多个独立的、可单独检索的子问题。
每个子问题应该是完整的、自包含的。

原始问题：{QUESTION}

输出JSON数组：["子问题1", "子问题2", ...]
直接输出JSON，不要解释。
```

### 策略三：多样化——同一个意思换几种说法

**适用场景**：知识库的表述风格和用户提问风格差异大。

知识库里可能用的是"接口响应时间优化"，用户问的是"怎么让API快一点"。虽然语义相近，但措辞差异可能导致向量检索的相似度不够高。

多样化的做法是：为同一个问题生成多个措辞不同的变体，每个变体都去检索，最后合并去重。

**示例**

```
原始问题：MySQL慢查询怎么优化

变体1：MySQL查询性能调优方案
变体2：数据库SQL执行效率提升方法
变体3：如何排查和解决MySQL慢SQL问题
```

知识库里不管用的是哪种表述，总有一个变体能命中。

:::tip 多样化的数量控制
一般生成3个变体就够了。太多会引入噪音，而且每个变体都要走一遍检索流程，延迟会线性增长。另外，原始问题一定要保留在检索列表中，防止变体偏离原意。
:::

**Prompt模板**

```
你是一名语义扩展专家。

为以下问题生成3个语义相同但措辞完全不同的变体，
用于提高知识库检索的召回率。

原始问题：{QUESTION}

输出JSON数组：["变体1", "变体2", "变体3"]
直接输出JSON，不要解释。
```

### 策略四：回溯——从具体问题退一步看全局

**适用场景**：问题太具体，知识库里没有直接对应的条目。

这个策略来自论文中的Step-Back Prompting，核心思想是：先把具体问题抽象成更通用的问题，用通用问题去检索，再结合具体情况回答。

**示例**

```
原始问题：我们项目用的是JDK 17 + Spring Boot 3.2，
         升级到Spring Boot 3.3后Actuator的health端点报错了

回溯后：Spring Boot 3.2到3.3的升级变更有哪些，
       Actuator模块有什么Breaking Change
```

知识库里大概率没有"JDK 17 + Spring Boot 3.2升级到3.3后Actuator报错"这么具体的文档，但很可能有Spring Boot版本升级指南。回溯后的问题更容易命中。

```
原始问题：我同事的电脑连不上公司VPN，显示证书过期

回溯后：VPN连接失败的常见原因和排查方法
```

**Prompt模板**

```
你是一个擅长抽象思维的专家。

将用户的具体问题转化为更通用、更本质的问题，
聚焦于背后的原理或规则，而不是具体细节。

原始问题：{QUESTION}

直接输出抽象后的问题，不要解释。
```

## 进阶技巧：HyDE——让假答案帮你找真文档

除了上面四种策略，还有一个很有意思的技巧叫HyDE（Hypothetical Document Embeddings，假设性文档嵌入）。

它的思路有点反直觉：**不直接用问题去检索，而是先让大模型"编"一个假答案，再用这个假答案去检索真文档**。

为什么这样做有效？因为假答案的文本风格和知识库里的真文档更接近。

**举个例子**

用户问："微服务之间怎么做数据一致性"

这个问题很短，向量化后的信息量有限。但如果让大模型先"编"一个假答案：

> 微服务之间的数据一致性通常通过分布式事务来保障。常见方案包括：Saga模式通过编排一系列本地事务实现最终一致性；TCC模式通过Try-Confirm-Cancel三阶段保证强一致性；基于消息队列的最终一致性方案通过可靠消息投递确保数据同步。在Spring Cloud生态中，可以使用Seata框架来实现分布式事务管理...

这个假答案虽然可能不完全准确，但它包含了"Saga"、"TCC"、"Seata"、"分布式事务"等关键术语，这些术语和知识库里的真实文档高度重合，用它去做向量检索，命中率会比原始问题高很多。

**HyDE的三步流程**

1. 收到用户问题后，先让大模型生成一个假设性答案（不要求准确，只要求风格接近）
2. 把假设性答案向量化，用它的向量去知识库检索
3. 把检索到的真实文档和用户原始问题一起交给大模型，生成最终答案

:::caution HyDE的适用边界
HyDE适合用户问题很短、很模糊的场景。但如果用户问题本身已经很具体（比如包含了错误码、类名等精确信息），HyDE反而可能引入噪音——假答案里的术语可能把检索方向带偏。所以实际使用时，可以先判断问题类型，再决定是否启用HyDE。
:::

## 代码实战：Spring AI的问题改写支持

Spring AI提供了`RetrievalAugmentationAdvisor`，其中内置了几种问题改写组件，可以直接拿来用。

### QueryTransformer：检索前的问题变换

Spring AI的`QueryTransformer`接口有三个实现：

**CompressionQueryTransformer——对话压缩（对应富化策略）**

它会把多轮对话历史和当前问题压缩成一个独立完整的查询，自动做指代消解。

```java
// 构造带历史的查询
Query query = Query.builder()
        .text("它的异步日志怎么配置？")
        .history(
            new UserMessage("Spring Boot默认用什么日志框架？"),
            new AssistantMessage("Spring Boot默认使用Logback作为日志框架。")
        )
        .build();

// 压缩改写
CompressionQueryTransformer transformer = CompressionQueryTransformer.builder()
        .chatClientBuilder(ChatClient.builder(chatModel).build().mutate())
        .build();

Query compressed = transformer.transform(query);
// 改写结果："Logback的异步日志如何配置？"
```

**RewriteQueryTransformer——问题精简（对应扩展策略）**

去除口语化表达中的冗余信息，让问题更适合检索。

```java
Query query = Query.builder()
        .text("就是那个，我想问一下，Spring里面那个AOP到底是怎么回事啊")
        .build();

RewriteQueryTransformer transformer = RewriteQueryTransformer.builder()
        .chatClientBuilder(ChatClient.builder(chatModel).build().mutate())
        .build();

Query rewritten = transformer.transform(query);
// 改写结果："Spring AOP的工作原理是什么"
```

**TranslationQueryTransformer——跨语言翻译**

如果知识库是英文的，用户用中文提问，可以先翻译再检索。

```java
TranslationQueryTransformer transformer = TranslationQueryTransformer.builder()
        .chatClientBuilder(ChatClient.builder(chatModel).build().mutate())
        .targetLanguage("en")
        .build();
```

### MultiQueryExpander：一个问题变多个（对应多样化策略）

```java
Query query = Query.builder()
        .text("Redis集群的数据分片策略")
        .build();

MultiQueryExpander expander = MultiQueryExpander.builder()
        .chatClientBuilder(ChatClient.builder(chatModel).build().mutate())
        .numberOfQueries(3)      // 生成3个变体
        .includeOriginal(true)   // 保留原始问题
        .build();

List<Query> expanded = expander.expand(query);
// 结果：原始问题 + 3个语义相近但措辞不同的变体
```

### 组装完整的改写流程

把这些组件串到`RetrievalAugmentationAdvisor`里：

```java
Advisor advisor = RetrievalAugmentationAdvisor.builder()
        // 检索前：压缩改写（处理多轮对话）
        .queryTransformers(
            CompressionQueryTransformer.builder()
                .chatClientBuilder(ChatClient.builder(chatModel).build().mutate())
                .build()
        )
        // 检索前：多样化扩展
        .queryExpander(
            MultiQueryExpander.builder()
                .chatClientBuilder(ChatClient.builder(chatModel).build().mutate())
                .numberOfQueries(3)
                .includeOriginal(true)
                .build()
        )
        // 检索
        .documentRetriever(
            VectorStoreDocumentRetriever.builder()
                .vectorStore(vectorStore)
                .topK(5)
                .similarityThreshold(0.6)
                .build()
        )
        // 文档合并去重
        .documentJoiner(new ConcatenationDocumentJoiner())
        .build();

String answer = chatClient.prompt()
        .advisors(advisor)
        .user("它的异步日志怎么配置？")
        .call()
        .content();
```

这段代码的执行流程是：先把多轮对话压缩成完整问题 → 再把完整问题扩展成多个变体 → 每个变体分别检索 → 合并去重 → 交给大模型生成回答。

## 自定义改写服务：更灵活的控制

Spring AI的内置组件覆盖了常见场景，但如果你需要更精细的控制（比如组合使用分解+多样化+回溯），可以自己实现一个改写服务：

```java
@Service
@Slf4j
public class QueryRewriteService {

    @Autowired
    private ChatModel chatModel;

    /** 问题分解 */
    public List<String> decompose(String question) {
        log.info("分解原始问题: {}", question);
        String prompt = """
            你是一名查询逻辑分析专家。
            将用户问题分解为多个独立的、可单独检索的子问题。
            输出JSON数组格式。

            原始问题：%s

            直接输出JSON数组。
            """.formatted(question);

        String result = chatModel.call(prompt);
        return JSON.parseArray(result, String.class);
    }

    /** 问题多样化 */
    public List<String> diversify(String question) {
        log.info("多样化问题: {}", question);
        String prompt = """
            为以下问题生成3个语义相同但措辞不同的变体。
            输出JSON数组格式。

            原始问题：%s
            """.formatted(question);

        String result = chatModel.call(prompt);
        return JSON.parseArray(result, String.class);
    }

    /** 问题回溯 */
    public String stepBack(String question) {
        log.info("回溯问题: {}", question);
        String prompt = """
            将具体问题转化为更通用的问题，
            聚焦于背后的原理或规则。

            原始问题：%s

            直接输出抽象后的问题。
            """.formatted(question);

        return chatModel.call(prompt);
    }

    /** 组合策略：回溯 + 分解 + 多样化 */
    public List<String> fullRewrite(String question) {
        List<String> allQueries = new ArrayList<>();
        allQueries.add(question); // 保留原始问题

        // 回溯
        String stepped = stepBack(question);
        allQueries.add(stepped);

        // 分解
        List<String> decomposed = decompose(question);
        allQueries.addAll(decomposed);

        // 对每个子问题做多样化
        for (String sub : decomposed) {
            allQueries.addAll(diversify(sub));
        }

        log.info("改写完成，共{}个检索词", allQueries.size());
        return allQueries;
    }
}
```

使用时，把改写结果逐个检索，合并去重：

```java
@GetMapping("/smartChat")
public String smartChat(@RequestParam String query) {
    List<String> rewrittenQueries = queryRewriteService.fullRewrite(query);

    // 用Set去重
    Set<Document> allDocs = new LinkedHashSet<>();
    for (String q : rewrittenQueries) {
        List<Document> docs = vectorStore.similaritySearch(
            SearchRequest.builder().query(q).topK(3).build()
        );
        allDocs.addAll(docs);
    }

    // 拼接文档内容，交给大模型
    String context = allDocs.stream()
            .map(Document::getText)
            .collect(Collectors.joining("\n\n---\n\n"));

    String prompt = """
        基于以下参考文档回答用户问题。
        如果文档中没有相关信息，请说明。

        参考文档：
        %s

        用户问题：%s
        """.formatted(context, query);

    return chatClient.prompt(prompt).call().content();
}
```

## 策略选择和性能权衡

### 什么时候用什么策略

| 问题特征 | 推荐策略 | 说明 |
| :--- | :--- | :--- |
| 多轮对话中有代词 | 富化 | 消除指代，补全上下文 |
| 口语化、简短 | 扩展/精简 | 补充完整信息 |
| 包含多个意图或需要多步推理 | 分解 | 拆成子问题分别检索 |
| 表述可能和知识库不一致 | 多样化 | 多种问法提高召回率 |
| 太具体，知识库没有直接答案 | 回溯 | 退一步找通用规则 |
| 问题很短很模糊 | HyDE | 用假答案扩充语义信息 |

### 性能优化建议

每种改写策略都需要调用一次大模型，策略越多延迟越高。几个实用的优化方向：

**并行执行**：分解和多样化可以并行调用

```java
CompletableFuture<String> stepBackFuture =
    CompletableFuture.supplyAsync(() -> rewriteService.stepBack(question));
CompletableFuture<List<String>> decomposeFuture =
    CompletableFuture.supplyAsync(() -> rewriteService.decompose(question));

CompletableFuture.allOf(stepBackFuture, decomposeFuture).join();
```

**按需启用**：简单问题只做扩展（1次调用），复杂问题才上全套

**缓存热门问题**：高频问题的改写结果可以缓存

**用小模型做改写**：问题改写不需要最强的模型，轻量模型速度更快、成本更低

:::caution 改写不是万能药
改写策略越多不等于效果越好。每多一种策略，就多一次大模型调用，延迟累加可能达到1-2秒。生产环境建议根据问题类型动态选择策略，而不是每次都全套上。另外，无论怎么改写，原始问题一定要保留在检索列表中——万一改写偏了，原始问题还能兜底。
:::

## 小结

问题改写是RAG优化中投入产出比很高的手段。四种核心策略各有侧重：

- 富化解决多轮对话的指代问题
- 分解处理复合问题和多跳推理
- 多样化弥合用户表达和知识库表述的差异
- 回溯把过于具体的问题抽象到可检索的层面

再加上HyDE这个进阶技巧，以及Spring AI提供的QueryTransformer和MultiQueryExpander等开箱即用的组件，基本能覆盖绝大多数场景。
