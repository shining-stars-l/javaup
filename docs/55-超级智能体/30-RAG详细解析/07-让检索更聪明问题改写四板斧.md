# 让检索更聪明：问题改写四板斧

## 翻译官的工作

想象你是一个翻译官，老板说的是方言，员工听的是普通话。

老板说："那个事儿弄得咋样了？"

你不能直接把这句话传达给员工——员工根本不知道"那个事儿"是什么。

你得先理解老板的意思，然后翻译成清晰的表达："上周让你们做的用户调研报告，进度怎么样了？"

问题改写在RAG中的角色就像这个翻译官——**把用户的原始提问，翻译成更适合检索的表达。**

## 为什么需要问题改写

### 用户提问的几个特点

**特点一：口语化、不规范**

用户会怎么问？

```
"那个报销的事儿咋弄"
"服务器挂了咋办"
"上次说的那个bug修了没"
```

这种口语化的表达，直接拿去做向量检索，效果通常不好。

**特点二：信息缺失**

多轮对话中，用户会省略很多信息：

```
第一轮：年假有多少天？
第二轮：怎么申请？  ← "申请什么"没说清楚
```

"怎么申请"这四个字单独拿去检索，能检索到什么？

**特点三：问题复杂**

有些问题包含多个子问题：

```
"请假流程是什么，另外我还剩几天年假"
```

这其实是两个问题：一个要查知识库（请假流程），一个要查业务系统（年假余额）。

**特点四：太具体**

有些问题太具体了，知识库里没有直接对应的内容：

```
"我表弟结婚，我能请几天假"
```

知识库里可能没有"表弟结婚"的具体条款，但有"婚丧假"的通用规定。

### 问题改写的目标

一句话概括：**让用户的自然语言提问，转化为更适合检索的查询表达。**

:::info 问题改写的作用
问题改写是RAG检索前的预处理步骤，本质是弥合"用户表达习惯"和"知识库表达方式"之间的差距。用户说"那个报销咋弄"，知识库里存的是"费用报销申请流程"——改写就是把前者转化为后者，提升检索命中率。
:::

## 四板斧：四种改写策略

问题改写的策略有很多，我总结了最常用的四种，管它叫"四板斧"。

### 第一斧：扩展——让问题更丰满

**什么情况用**

用户的问题太简短、太口语化，需要补充完整。

**怎么做**

让大模型把简短的问题扩展成完整、规范的表达。

**示例**

```
原始问题：报销咋弄
扩展后：公司的报销流程是什么，需要准备哪些材料，如何提交报销申请
```

```
原始问题：服务器挂了
扩展后：服务器宕机故障的排查步骤是什么，如何恢复服务器正常运行
```

**Prompt模板**

```
你是一个问题改写专家。

请将用户的口语化问题改写为更完整、更规范、更适合检索的表达。
要求：
1. 保持原意不变
2. 补充必要的上下文
3. 使用规范的书面语

原始问题：{QUESTION}

请直接输出改写后的问题，不要解释。
```

### 第二斧：分解——把大问题拆成小问题

**什么情况用**

问题很复杂，包含多个子问题，或者是需要多步推理的"多跳问题"。

**怎么做**

让大模型把复杂问题拆解成多个独立的子问题，每个子问题单独检索。

**示例一：多意图问题**

```
原始问题：Kafka和RocketMQ有什么区别，哪个更适合我们的场景

分解后：
1. Kafka的核心特性和适用场景是什么
2. RocketMQ的核心特性和适用场景是什么
3. Kafka和RocketMQ在性能、可靠性、生态方面的对比
```

**示例二：多跳问题**

```
原始问题：iPhone 15发布时，苹果的CEO是谁

分解后：
1. iPhone 15是什么时候发布的
2. 2023年9月，苹果公司的CEO是谁
```

**Prompt模板**

```
你是一名专业的查询逻辑分析专家。

请将用户的复杂问题分解为多个独立的、可单独检索的子问题。

要求：
1. 每个子问题应该是独立的、完整的
2. 子问题之间有逻辑关联
3. 输出JSON数组格式

原始问题：{QUESTION}

输出格式：
["子问题1", "子问题2", "子问题3"]

请直接输出JSON数组，不要解释。
```

### 第三斧：多样化——一个问题多种问法

**什么情况用**

知识库里的表述方式可能和用户的问法不一样，需要多种表达来提高召回率。

**怎么做**

为同一个问题生成多个语义相近但措辞不同的变体，每个变体都去检索，最后合并结果。

**示例**

```
原始问题：怎么提高接口性能

变体1：接口响应速度优化方案
变体2：API性能调优最佳实践
变体3：如何降低接口延迟
```

知识库里可能用的是"响应速度优化"而不是"提高性能"，有了多个变体，命中概率就高了。

:::tip 多样化策略提升召回率
多样化改写（Query Diversification）能显著提升检索召回率，特别适合知识库描述风格和用户提问风格差异较大的场景。一般生成3个变体就够了，太多反而会引入噪音，而且增加大模型调用次数和延迟。
:::

**Prompt模板**

```
你是一名专业的语义扩展专家。

请为给定的问题生成3个语义相同但措辞不同的变体，以提高检索召回率。

要求：
1. 保持语义一致
2. 使用不同的词汇和表达方式
3. 输出JSON数组格式

原始问题：{QUESTION}

输出格式：
["变体1", "变体2", "变体3"]

请直接输出JSON数组。
```

### 第四斧：回溯——从具体到抽象

**什么情况用**

用户的问题太具体，知识库里没有直接对应的内容，需要回溯到更通用的层面。

**怎么做**

先把具体问题抽象成通用问题，用通用问题去检索，再结合具体情况回答。

**示例**

```
原始问题：我表弟结婚，我能请几天假

回溯后：婚丧假的请假规定是什么

（检索到婚丧假规定后，再根据"表弟"的亲属关系判断具体天数）
```

```
原始问题：上海到北京的高铁要多久

回溯后：中国高铁的平均时速和主要线路有哪些
```

**Prompt模板**

```
你是一个擅长抽象思维的专家。

请将用户的具体问题转化为更通用、更本质的问题，便于在知识库中检索到相关信息。

要求：
1. 提取问题背后的通用原理或规则
2. 不要过度抽象，保持和原问题的关联
3. 只输出转化后的问题

原始问题：{QUESTION}

请直接输出抽象后的问题。
```

## 实战：企业HR助手

来看一个完整的实战案例——企业HR助手。

### 场景描述

公司内部的HR知识库，包含各种人事制度：
- 请假制度
- 薪酬福利
- 入职离职流程
- 绩效考核
- ...

员工可以用自然语言提问，系统返回相关的政策解读。

### 实现问题改写服务

```java
@Service
@Slf4j
public class QueryRewriteService {

    @Autowired
    private ChatModel chatModel;

    /**
     * 问题扩展
     */
    public String expand(String question) {
        String prompt = """
            你是一个问题改写专家。
            请将用户的口语化问题改写为更完整、更规范的表达。
            
            原始问题：%s
            
            请直接输出改写后的问题。
            """.formatted(question);
        
        return chatModel.call(prompt);
    }

    /**
     * 问题分解
     */
    public List<String> decompose(String question) {
        String prompt = """
            你是一名查询逻辑分析专家。
            请将复杂问题分解为多个独立的子问题。
            输出JSON数组格式：["子问题1", "子问题2"]
            
            原始问题：%s
            """.formatted(question);
        
        String result = chatModel.call(prompt);
        return JSON.parseArray(result, String.class);
    }

    /**
     * 问题多样化
     */
    public List<String> diversify(String question) {
        String prompt = """
            请为以下问题生成3个语义相同但措辞不同的变体。
            输出JSON数组格式。
            
            原始问题：%s
            """.formatted(question);
        
        String result = chatModel.call(prompt);
        return JSON.parseArray(result, String.class);
    }

    /**
     * 问题回溯
     */
    public String stepBack(String question) {
        String prompt = """
            请将具体问题转化为更通用的问题。
            
            原始问题：%s
            
            请直接输出通用问题。
            """.formatted(question);
        
        return chatModel.call(prompt);
    }
}
```

### 组合使用策略

不同的问题需要不同的改写策略，可以组合使用：

```java
@Service
public class SmartQueryRewriteService {

    @Autowired
    private QueryRewriteService rewriteService;
    
    @Autowired
    private VectorStore vectorStore;

    /**
     * 智能检索：根据问题特点选择改写策略
     */
    public List<Document> smartSearch(String question) {
        Set<Document> allResults = new LinkedHashSet<>();
        
        // 策略1：先回溯到通用问题
        String generalQuestion = rewriteService.stepBack(question);
        allResults.addAll(search(generalQuestion));
        
        // 策略2：分解成子问题
        List<String> subQuestions = rewriteService.decompose(question);
        for (String subQ : subQuestions) {
            allResults.addAll(search(subQ));
        }
        
        // 策略3：对每个子问题做多样化
        for (String subQ : subQuestions) {
            List<String> variations = rewriteService.diversify(subQ);
            for (String v : variations) {
                allResults.addAll(search(v));
            }
        }
        
        return new ArrayList<>(allResults);
    }
    
    private List<Document> search(String query) {
        return vectorStore.similaritySearch(
            SearchRequest.builder()
                .query(query)
                .topK(3)
                .similarityThreshold(0.6)
                .build()
        );
    }
}
```

### 效果对比

**测试问题**："我老婆生孩子，能请多少天假"

**不使用改写**：

直接检索"我老婆生孩子，能请多少天假"，可能检索不到任何结果（知识库里可能没有完全匹配的表述）。

**使用改写**：

```
回溯：员工配偶生育的休假政策是什么
分解：
  1. 陪产假的天数规定
  2. 陪产假的申请条件和流程
多样化：
  - 男员工陪产假规定
  - 配偶分娩休假制度
  - 爸爸假期政策
```

多个检索词同时出击，命中率大大提高。

## 策略选择指南

### 什么时候用什么策略

| 问题特点 | 推荐策略 | 原因 |
| :--- | :--- | :--- |
| 口语化、简短 | 扩展 | 补充完整信息 |
| 包含多个意图 | 分解 | 分别检索，避免遗漏 |
| 需要多步推理 | 分解 | 逐步求解 |
| 表述可能和知识库不一致 | 多样化 | 提高召回率 |
| 太具体，可能没有直接答案 | 回溯 | 找到相关的通用规则 |
| 多轮对话中的指代问题 | 扩展（结合上下文） | 消除歧义 |

### 组合使用的建议

实际项目中，我通常会组合使用多种策略：

```
原始问题
    ↓
回溯（如果问题很具体）
    ↓
分解（如果问题复杂）
    ↓
多样化（对每个子问题）
    ↓
合并检索结果
```

但要注意：**策略越多，调用大模型的次数越多，延迟越高**。

要在效果和性能之间找平衡。

:::caution 改写策略越多不等于越好
每增加一种改写策略，就多一次大模型调用，延迟累加可能达到1-2秒。生产环境建议：简单问题只做扩展（1次调用），复杂问题做分解+多样化（2-3次调用），并尽量并行执行。另外，原始问题一定要保留在检索词列表中，防止改写偏差导致漏召回。
:::

## 性能优化

### 问题：改写太慢

问题改写需要调用大模型，每次调用都有延迟。如果又是分解、又是多样化，可能要调用好几次。

### 优化方案

**方案一：并行调用**

分解和多样化可以并行执行：

```java
CompletableFuture<String> stepBackFuture = CompletableFuture.supplyAsync(
    () -> rewriteService.stepBack(question)
);

CompletableFuture<List<String>> decomposeFuture = CompletableFuture.supplyAsync(
    () -> rewriteService.decompose(question)
);

// 等待所有任务完成
CompletableFuture.allOf(stepBackFuture, decomposeFuture).join();
```

**方案二：缓存常见问题的改写结果**

如果某些问题经常被问到，可以把改写结果缓存起来：

```java
@Cacheable(value = "queryRewrite", key = "#question")
public List<String> rewrite(String question) {
    // 改写逻辑
}
```

**方案三：简化策略**

不是每个问题都需要全套策略。可以先判断问题类型，再选择性地使用：

```java
public List<String> rewrite(String question) {
    // 简单问题：只做扩展
    if (isSimpleQuestion(question)) {
        return List.of(rewriteService.expand(question));
    }
    
    // 复杂问题：分解 + 多样化
    return fullRewrite(question);
}
```

**方案四：用小模型做改写**

问题改写不需要特别强的模型，用轻量级的模型就够了，速度更快。

## 常见问题

### Q1：改写后的问题会不会偏离原意？

有可能。所以原始问题也要保留，作为检索词之一。

最终的检索词列表应该包括：
- 原始问题
- 改写后的问题

这样即使改写不准，也不会完全偏离。

### Q2：改写策略用错了怎么办？

没关系，多检索几次，合并去重就好。

关键是要有兜底：无论改写成什么样，原始问题一定要保留。

### Q3：改写会增加多少延迟？

取决于：
- 使用的模型（大模型慢，小模型快）
- 策略数量（策略越多，调用次数越多）
- 是否并行

我的经验：单次改写大概100-500ms，如果策略用得多可能要1-2秒。

对于实时问答场景，这个延迟是可以接受的（反正等大模型生成回答也要几秒）。

## 小结

这篇文章讲了问题改写的四板斧：

1. **扩展**：把简短、口语化的问题补充完整
2. **分解**：把复杂问题拆成多个简单问题
3. **多样化**：一个问题多种问法，提高召回率
4. **回溯**：从具体问题抽象出通用问题

问题改写是**投入产出比很高**的优化手段。实现不复杂，但对检索效果的提升很明显。

:::tip 问题改写是高性价比优化
相比于更换更好的Embedding模型或引入重排序，问题改写的实现门槛低、收益高，是RAG优化的优先项。特别是对于企业内部的HR、IT支持等场景，用户提问口语化严重，问题改写往往能带来30%以上的检索命中率提升。
:::
