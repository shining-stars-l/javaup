# 混合检索：语义+关键词双保险

## 纯向量检索的尴尬时刻

前面几篇咱们一直在聊向量检索有多厉害——能理解语义、能处理同义词、能跨语言匹配。但真跑起来你就会发现，有些场景它会让你很头疼。

举个例子吧。假设你在给公司搭一个代码仓库的智能问答系统，开发同学问：`PaymentService` 的 `processRefund` 方法在哪个文件？

你把这个问题向量化后去检索，返回的结果可能是：

- 退款流程设计文档
- 支付模块架构说明
- 订单服务接口定义
- 退货业务流程图
- 支付网关对接指南

看起来都和"支付"、"退款"相关，但没有一个直接告诉你 `PaymentService.java` 在哪、`processRefund` 方法长什么样。向量检索把你的问题理解成了"退款相关的东西"，完美避开了你真正想要的那个精确的类名和方法名。

再来一个更扎心的。用户问：`NullPointerException at line 127 in OrderController.java` 怎么解决？

向量检索返回：

- Java 常见异常处理指南
- 空指针异常排查思路
- Spring MVC 控制器最佳实践
- 异常日志配置说明

好家伙，全是"正确的废话"。用户要的是 `OrderController.java` 第 127 行那个具体的问题，你给人家返回一堆通用教程，这不是答非所问吗？

这就是纯向量检索的短板：**它太会"理解"了，反而丢掉了精确信息**。

## 中西医结合的智慧

这种情况让我想起了看病。

西医讲究精准定位——你发烧，先量体温，38.5°C；你说肚子疼，做个 CT 看看是阑尾还是胆囊。它追求的是**精确匹配**，找到那个具体的病灶。

中医讲究整体把握——你脸色发黄、舌苔厚腻、脉象滑数，综合起来判断是湿热内蕴。它追求的是**语义理解**，把各种症状串起来看整体。

单靠西医，可能漏掉一些"说不清道不明"但确实存在的问题；单靠中医，可能在需要精准定位的时候差点意思。所以现在很多医院都搞"中西医结合"，取长补短。

混合检索就是 RAG 里的"中西医结合"：

- **向量检索**像中医，擅长理解语义、把握整体
- **关键词检索**像西医，擅长精确匹配、定位具体

把两者结合起来，就能兼顾"理解用户意图"和"找到精确信息"。

## BM25：关键词检索的扛把子

说到关键词检索，就不得不提 BM25 这个算法。它是搜索引擎的默认排序算法，Google、Elasticsearch 都在用。

### 核心思想：稀有词更有价值

BM25 的核心逻辑其实很朴素：**如果一个词在某个文档里出现得多，而且在其他文档里出现得少，那这个词对于定位这个文档就很有价值**。

用代码仓库的例子来说：

- `PaymentService` 这个词可能只在支付模块的几个文档里出现，它的"区分度"就很高
- `public`、`void`、`return` 这些词到处都是，它们的"区分度"就很低

BM25 会给高区分度的词更高的权重，所以当你搜 `PaymentService processRefund` 的时候，它能快速锁定那个包含这两个词的文档。

### 三个关键因素

BM25 在打分的时候会考虑三件事：

**1. 词频（TF）：出现越多越相关，但有上限**

如果一个文档里 `PaymentService` 出现了 5 次，另一个只出现 1 次，前者大概率更相关。但这个"越多越好"是有上限的——出现 100 次不会比出现 10 次好 10 倍，避免有人刷词作弊。

**2. 逆文档频率（IDF）：越稀有越有价值**

`PaymentService` 在整个知识库里只出现在 3 个文档中，`service` 出现在 500 个文档中。搜 `PaymentService` 的时候，前者的权重会比后者高很多，因为它更能帮你锁定目标。

**3. 文档长度归一化：长文档不能占便宜**

一个 5000 字的设计文档天然比 500 字的接口说明包含更多词，但这不代表它就更相关。BM25 会按文档长度做归一化，让长短文档站在同一起跑线上。

### BM25 vs 向量检索：不是谁替代谁

把两种检索方式放在一起对比，你就能看出它们的互补关系：

| 维度 | BM25 关键词检索 | 向量检索 |
|:-----|:----------------|:---------|
| 擅长场景 | 精确关键词、类名方法名、错误码、版本号 | 语义理解、同义词、意图匹配 |
| 典型问题 | `PaymentService` 在哪个模块？ | 怎么处理支付失败的情况？ |
| 短板 | 无法理解语义，"退款"和"返还金额"匹配不上 | 对精确关键词不敏感，容易丢失具体信息 |
| 底层原理 | 统计词频和文档频率，计算关键词重要性 | 把文本转成向量，计算语义相似度 |
| 计算成本 | 低，只需要统计词频 | 高，需要调用 Embedding 模型 |

看完这个表，结论就很清楚了：**它们不是竞争关系，而是互补关系**。

## 混合检索：两条路同时走

混合检索的核心思路很简单：**同时跑向量检索和关键词检索，把两路结果融合成一个最终排序**。

用技术文档搜索的场景来说，当用户问 `SpringBoot 启动时 bean 循环依赖怎么解决` 的时候：

- **向量检索**会找到：Spring 依赖注入原理、Bean 生命周期管理、IOC 容器工作机制……这些语义相关的内容
- **关键词检索**会找到：包含 `循环依赖`、`SpringBoot`、`bean` 这些具体词的文档

把两路结果合起来，既能覆盖语义相关的内容，又不会漏掉那些精确匹配的文档。

### 两种架构方案

混合检索在工程上有两种实现方式：

**方案一：Milvus 原生混合检索（推荐）**

Milvus 2.5+ 版本内置了 BM25 全文检索能力，一个系统同时搞定向量检索和关键词检索。

优点：
- 架构简单，一套系统解决问题
- 数据不用双写，没有一致性问题
- 原生支持 RRF 融合，API 调用简单
- 运维成本低

缺点：
- 全文检索能力比 Elasticsearch 弱一些
- 中文分词能力有限
- 查询语法不如 ES 丰富

**方案二：Elasticsearch + Milvus 双系统**

ES 负责关键词检索，Milvus 负责向量检索，应用层做结果融合。

优点：
- ES 的全文检索能力成熟强大
- 中文分词生态好（IK 分词器、HanLP 等）
- 查询语法丰富，支持复杂的布尔查询

缺点：
- 需要维护两套系统，运维复杂
- 数据双写带来一致性问题
- 融合逻辑需要自己实现

**怎么选？**

| 场景 | 推荐方案 |
|:-----|:---------|
| 快速验证、团队规模小 | Milvus 原生方案 |
| 对中文分词要求高 | ES + Milvus |
| 已有 ES 基础设施 | ES + Milvus |
| 需要复杂查询语法 | ES + Milvus |

这篇咱们用 Milvus 原生方案来讲，降低上手门槛。

## 分数融合的坑：两种分数没法直接比

混合检索有个技术难题：**两种检索的分数不在同一个尺度上**。

向量检索返回的是余弦相似度，范围是 0 到 1；BM25 返回的是相关性分数，可能是 0 到几十甚至上百。

你不能直接把它们相加——向量检索说这个文档 0.85 分，BM25 说 12.3 分，加起来 13.15 分，这个数字毫无意义。

你可能想到做归一化——把两种分数都映射到 0~1 之间再比较。但这也有问题：
- 如果某一路的分数分布很集中（都在 0.8~0.9），归一化会把微小差异放大
- 如果分数分布很分散（0.1~0.9 都有），归一化会把大差异压缩

所以实际工程中，最常用的融合策略不是基于分数，而是基于排名——这就是 **RRF（Reciprocal Rank Fusion，倒数排名融合）**。

## RRF：只看排名，不看分数

RRF 的核心思想特别直接：**一个结果在两路检索中排名都靠前，那它大概率是最相关的**。

计算公式也很简单：

```
RRF(d) = Σ 1 / (k + rank_i(d))
```

其中：
- `rank_i(d)` 是某个文档在第 i 路检索中的排名（从 1 开始）
- `k` 是一个平滑常数，通常取 60
- `Σ` 表示对所有检索路求和

### 举个例子

假设向量检索返回 [A, B, C, D, E]，关键词检索返回 [C, A, F, B, G]，怎么用 RRF 融合？

| 文档 | 向量检索排名 | 关键词检索排名 | RRF 分数（k=60） |
|:-----|:-------------|:---------------|:-----------------|
| A | 1 | 2 | 1/61 + 1/62 = 0.0325 |
| C | 3 | 1 | 1/63 + 1/61 = 0.0323 |
| B | 2 | 4 | 1/62 + 1/64 = 0.0317 |
| F | - | 3 | 1/63 = 0.0159 |
| D | 4 | - | 1/64 = 0.0156 |
| E | 5 | - | 1/65 = 0.0154 |
| G | - | 5 | 1/65 = 0.0154 |

按 RRF 分数从高到低排序：**A、C、B、F、D、E、G**。

你会发现 A 和 C 排到了最前面，因为它们在两路检索中都排名靠前。只在一路出现的文档（F、D、E、G）排在后面。这正是混合检索想要的效果。

### 为什么 RRF 效果好

- 不需要做复杂的分数归一化
- 对异常高分不敏感
- 工程上稳定、好调试、好解释
- 学术界和工业界都验证过效果

## 代码实战：代码仓库智能问答

咱们用一个"代码仓库智能问答"的场景来跑一遍完整的混合检索流程。

【截图提示：在 IDE 中运行混合检索代码，展示控制台输出】

```java
/**
 * 代码仓库智能问答 - 混合检索实现
 * 支持三种检索模式的对比：纯向量、纯BM25、混合RRF
 */
public class CodeRepoHybridSearch {

    private static final String COLLECTION = "code_repo_docs";
    private static final String EMBEDDING_API_KEY = "你的API Key";
    private static final String EMBEDDING_URL = "https://api.siliconflow.cn/v1/embeddings";
    private static final String EMBEDDING_MODEL = "Qwen/Qwen3-Embedding-8B";

    private static final Gson GSON = new Gson();
    private static final OkHttpClient HTTP_CLIENT = new OkHttpClient();

    /**
     * 三种检索模式
     */
    public enum SearchMode {
        DENSE_ONLY,     // 纯向量检索：理解语义
        SPARSE_ONLY,    // 纯BM25检索：精确匹配
        HYBRID          // 混合检索：两者兼顾
    }

    /**
     * 检索参数配置
     */
    @Data
    @Builder
    public static class SearchConfig {
        @Builder.Default
        private int denseTopK = 20;          // 向量检索召回数
        @Builder.Default
        private int sparseTopK = 20;         // BM25检索召回数
        @Builder.Default
        private int finalTopK = 5;           // 最终返回数
        @Builder.Default
        private int rrfK = 60;               // RRF平滑常数
        @Builder.Default
        private List<String> outputFields = List.of("content", "file_path", "doc_type");
    }

    public static void main(String[] args) {
        MilvusClientV2 client = new MilvusClientV2(ConnectConfig.builder()
                .uri("http://localhost:19530")
                .build());

        // 初始化Collection并加载数据
        initCollectionAndData(client);

        // 测试不同类型的问题
        List<String> testQueries = List.of(
                "PaymentService 的 processRefund 方法在哪个文件",
                "怎么处理支付超时的情况",
                "NullPointerException at OrderController line 127",
                "Spring 事务传播机制怎么配置"
        );

        SearchConfig config = SearchConfig.builder().build();

        for (String query : testQueries) {
            System.out.println("\n========================================");
            System.out.println("问题：" + query);
            System.out.println("========================================");

            // 三种模式对比
            for (SearchMode mode : SearchMode.values()) {
                SearchResp resp = runSearch(client, query, mode, config);
                printResults(resp, mode);
            }
        }
    }

    /**
     * 创建Collection并加载示例数据
     */
    private static void initCollectionAndData(MilvusClientV2 client) {
        Boolean exists = client.hasCollection(
                HasCollectionReq.builder().collectionName(COLLECTION).build()
        );

        if (Boolean.TRUE.equals(exists)) {
            client.loadCollection(LoadCollectionReq.builder()
                    .collectionName(COLLECTION).build());
            System.out.println("Collection 已存在，直接加载");
            return;
        }

        // 创建Schema
        CreateCollectionReq.CollectionSchema schema = client.createSchema();

        schema.addField(AddFieldReq.builder()
                .fieldName("id").dataType(DataType.Int64)
                .isPrimaryKey(true).autoID(true).build());

        // 文档内容字段，启用分词器用于BM25
        schema.addField(AddFieldReq.builder()
                .fieldName("content").dataType(DataType.VarChar)
                .maxLength(8192).enableAnalyzer(true).build());

        // 文件路径
        schema.addField(AddFieldReq.builder()
                .fieldName("file_path").dataType(DataType.VarChar)
                .maxLength(512).build());

        // 文档类型：code、doc、config
        schema.addField(AddFieldReq.builder()
                .fieldName("doc_type").dataType(DataType.VarChar)
                .maxLength(32).build());

        // 密集向量字段
        schema.addField(AddFieldReq.builder()
                .fieldName("content_dense").dataType(DataType.FloatVector)
                .dimension(4096).build());

        // 稀疏向量字段（BM25自动生成）
        schema.addField(AddFieldReq.builder()
                .fieldName("content_sparse").dataType(DataType.SparseFloatVector).build());

        // BM25函数配置
        schema.addFunction(Function.builder()
                .functionType(FunctionType.BM25)
                .name("content_bm25")
                .inputFieldNames(List.of("content"))
                .outputFieldNames(List.of("content_sparse"))
                .build());

        // 创建Collection
        client.createCollection(CreateCollectionReq.builder()
                .collectionName(COLLECTION).collectionSchema(schema).build());

        // 创建索引
        IndexParam denseIndex = IndexParam.builder()
                .fieldName("content_dense")
                .indexType(IndexParam.IndexType.AUTOINDEX)
                .metricType(IndexParam.MetricType.COSINE).build();

        IndexParam sparseIndex = IndexParam.builder()
                .fieldName("content_sparse")
                .indexType(IndexParam.IndexType.AUTOINDEX)
                .metricType(IndexParam.MetricType.BM25).build();

        client.createIndex(CreateIndexReq.builder()
                .collectionName(COLLECTION)
                .indexParams(List.of(denseIndex, sparseIndex)).build());

        // 插入示例数据
        List<JsonObject> rows = prepareCodeRepoDocs();
        client.insert(InsertReq.builder()
                .collectionName(COLLECTION).data(rows).build());

        client.loadCollection(LoadCollectionReq.builder()
                .collectionName(COLLECTION).build());

        System.out.println("Collection 创建完成，已插入 " + rows.size() + " 条数据");
    }

            row.addProperty("doc_type", doc.get("doc_type"));

            // 生成密集向量
            List<Float> vector = getEmbedding(doc.get("content"));
            JsonArray arr = new JsonArray();
            vector.forEach(arr::add);

    /**
     * 执行检索
     */
    @SneakyThrows
    private static SearchResp runSearch(MilvusClientV2 client, String query,
                                        SearchMode mode, SearchConfig config) {
        return switch (mode) {
            case DENSE_ONLY -> runDenseSearch(client, query, config);
            case SPARSE_ONLY -> runSparseSearch(client, query, config);
            case HYBRID -> runHybridSearch(client, query, config);
        };
    }

    /**
     * 纯向量检索
     */
    private static SearchResp runDenseSearch(MilvusClientV2 client, String query,
                                             SearchConfig config) throws Exception {
        List<Float> queryVec = getEmbedding(query);

        return client.search(SearchReq.builder()
                .collectionName(COLLECTION)
                .annsField("content_dense")
                .data(Collections.singletonList(new FloatVec(queryVec)))
                .topK(config.getFinalTopK())
                .outputFields(config.getOutputFields())
                .build());
    }

    /**
     * 纯BM25检索
     */
    private static SearchResp runSparseSearch(MilvusClientV2 client, String query,
                                              SearchConfig config) {
        return client.search(SearchReq.builder()
                .collectionName(COLLECTION)
                .annsField("content_sparse")
                .data(Collections.singletonList(new EmbeddedText(query)))
                .topK(config.getFinalTopK())
                .outputFields(config.getOutputFields())
                .build());
    }

    /**
     * 混合检索：Dense + Sparse + RRF融合
     */
    private static SearchResp runHybridSearch(MilvusClientV2 client, String query,
                                              SearchConfig config) throws Exception {
        List<Float> queryVec = getEmbedding(query);

        // 向量检索请求
        AnnSearchReq denseReq = AnnSearchReq.builder()
                .vectorFieldName("content_dense")
                .vectors(Collections.singletonList(new FloatVec(queryVec)))
                .topK(config.getDenseTopK())
                .build();

        // BM25检索请求
        AnnSearchReq sparseReq = AnnSearchReq.builder()
                .vectorFieldName("content_sparse")
                .vectors(Collections.singletonList(new EmbeddedText(query)))
                .topK(config.getSparseTopK())
                .build();

        // 混合检索 + RRF融合
        HybridSearchReq hybridReq = HybridSearchReq.builder()
                .collectionName(COLLECTION)
                .searchRequests(List.of(denseReq, sparseReq))
                .ranker(new RRFRanker(config.getRrfK()))
                .topK(config.getFinalTopK())
                .outFields(config.getOutputFields())
                .build();

        return client.hybridSearch(hybridReq);
    }

    /**
     * 打印检索结果
     */
    private static void printResults(SearchResp resp, SearchMode mode) {
        System.out.println("\n--- " + mode + " ---");
        List<List<SearchResp.SearchResult>> results = resp.getSearchResults();

        for (List<SearchResp.SearchResult> oneQueryResults : results) {
            for (int i = 0; i < oneQueryResults.size(); i++) {
                SearchResp.SearchResult r = oneQueryResults.get(i);
                Map<String, Object> entity = r.getEntity();

                String filePath = entity.get("file_path").toString();
                String content = entity.get("content").toString();
                // 截断内容，只显示前80个字符
                String shortContent = content.length() > 80
                        ? content.substring(0, 80) + "..."
                        : content;

                System.out.printf("Top-%d [%.4f] %s%n", i + 1, r.getScore(), filePath);
                System.out.println("       " + shortContent);
            }
        }
    }

    /**
     * 调用Embedding API
     */
    private static List<Float> getEmbedding(String text) throws Exception {
        JsonObject body = new JsonObject();
        body.addProperty("model", EMBEDDING_MODEL);
        body.add("input", GSON.toJsonTree(List.of(text)));

        Request request = new Request.Builder()
                .url(EMBEDDING_URL)
                .addHeader("Authorization", "Bearer " + EMBEDDING_API_KEY)
                .addHeader("Content-Type", "application/json")
                .post(RequestBody.create(GSON.toJson(body), MediaType.parse("application/json")))
                .build();

        try (Response response = HTTP_CLIENT.newCall(request).execute()) {
            String respBody = response.body().string();
            JsonObject json = GSON.fromJson(respBody, JsonObject.class);
            JsonArray embedding = json.getAsJsonArray("data")
                    .get(0).getAsJsonObject()
                    .getAsJsonArray("embedding");

            List<Float> vector = new ArrayList<>();
            embedding.forEach(e -> vector.add(e.getAsFloat()));
            return vector;
        }
    }
}
```

### 运行结果分析

用几个典型问题跑一下，看看三种检索模式的差异：

**问题1：`PaymentService 的 processRefund 方法在哪个文件`**

| 模式 | Top-1 结果 |
|:-----|:-----------|
| 纯向量 | docs/payment/design.md（支付模块设计文档） |
| 纯BM25 | src/main/java/.../PaymentService.java |
| 混合 | src/main/java/.../PaymentService.java |

纯向量检索把问题理解成"支付相关"，返回了设计文档；BM25 精确匹配到了 `PaymentService` 和 `processRefund`，直接命中源码文件；混合检索两路都参与，BM25 的精确匹配帮助 Top-1 定位到正确答案。

**问题2：`怎么处理支付超时的情况`**

| 模式 | Top-1 结果 |
|:-----|:-----------|
| 纯向量 | docs/payment/timeout-handling.md |
| 纯BM25 | docs/payment/timeout-handling.md |
| 混合 | docs/payment/timeout-handling.md |

这种语义明确的问题，三种模式都能找对。但如果知识库里有个文档标题是"网络请求超时重试"（不包含"支付"但语义相关），向量检索可能会把它排得更靠前。

**问题3：`NullPointerException at OrderController line 127`**

| 模式 | Top-1 结果 |
|:-----|:-----------|
| 纯向量 | docs/java/npe-best-practice.md（通用最佳实践） |

这是个典型案例。纯向量检索理解了"空指针异常"的语义，返回了通用的最佳实践文档；BM25 精确匹配到了 `OrderController`、`127`、`NullPointerException` 这些具体词，直接找到了问题记录；混合检索兼顾两者，正确答案排在第一。

## 不同问题类型的检索策略

根据问题的类型，三种检索模式的表现会有明显差异：

| 问题类型 | 示例 | 最优策略 | 原因 |
|:---------|:-----|:---------|:-----|
| 精确定位类 | `XXXService` 在哪个包 | BM25/混合 | 需要精确匹配类名 |
| 概念理解类 | 依赖注入的原理是什么 | 向量/混合 | 需要语义理解 |
| 错误排查类 | 某行代码报错怎么解决 | 混合 | 既要匹配错误信息，也要理解问题 |
| 配置查询类 | 某参数怎么配置 | 混合 | 既要匹配参数名，也要理解配置场景 |

实际业务中，用户的问题五花八门，你没法预判他会问哪种类型。所以**混合检索是最稳的选择**——它不一定在每种场景都是最优，但它在所有场景都不会太差。

## 检索参数调优指南

给一组可以直接上线的经验值：

| 参数 | 建议值 | 调优方向 |
|:-----|:-------|:---------|
| 向量检索 TopK | 20 | 漏召回就加大，延迟高就减小 |
| BM25 TopK | 20 | 问题包含关键词多时可以加到 40 |
| RRF k 值 | 60 | 一般不用改，这是业界标准值 |
| 最终返回 K | 5 | 结合大模型上下文窗口调整 |

### 调优顺序很重要

很多人一上来就调参数，其实有个正确的顺序：

**1. 先看召回覆盖率**

检查 Top-20 或 Top-50 的候选集里，是否包含了正确答案。如果连召回都漏了，后面怎么调都没用。

**2. 再看排序精度**

在召回没问题的前提下，看正确答案是否排在前几位。如果排在第 10 位，说明排序有问题。

**3. 最后看业务指标**

人工标注准确率、用户追问率、答非所问率。这些才是最终衡量标准。

### 一个容易踩的坑

召回阶段漏掉了，后面怎么重排都救不回来。

很多团队一上来就加 Reranker（重排序模型），结果其实是召回阶段已经把正确答案漏掉了。正确的做法是：**先保证召回覆盖，再优化排序精度**。

## Spring AI 集成方案

如果你用的是 Spring AI 框架，可以通过 `QuestionAnswerAdvisor` 和自定义的 `VectorStore` 来实现混合检索。

【截图提示：Spring AI项目结构和配置文件】

```java
/**
 * Spring AI 混合检索配置
 */
@Configuration
public class HybridSearchConfig {

    @Bean
    public MilvusServiceClient milvusClient() {
        return new MilvusServiceClient(ConnectParam.newBuilder()
                .withUri("http://localhost:19530")
                .build());
    }

    @Bean
    public VectorStore vectorStore(MilvusServiceClient client,
                                   EmbeddingModel embeddingModel) {
        // 自定义MilvusVectorStore，支持混合检索
        return new HybridMilvusVectorStore(client, embeddingModel,
                HybridSearchOptions.builder()
                        .enableBm25(true)
                        .rrfK(60)
                        .build());
    }

    @Bean
    public ChatClient chatClient(ChatModel chatModel, VectorStore vectorStore) {
        return ChatClient.builder(chatModel)
                .defaultAdvisors(
                        new QuestionAnswerAdvisor(vectorStore,
                                SearchRequest.builder()
                                        .topK(5)
                                        .build())
                )
                .build();
    }
}

/**
 * 自定义混合检索VectorStore
 */
public class HybridMilvusVectorStore implements VectorStore {

    private final MilvusServiceClient client;
    private final EmbeddingModel embeddingModel;
    private final HybridSearchOptions options;

    @Override
    public List<Document> similaritySearch(SearchRequest request) {
        String query = request.getQuery();
        int topK = request.getTopK();

        // 1. 生成查询向量
        float[] queryVector = embeddingModel.embed(query);

        // 2. 构建混合检索请求
        List<AnnSearchReq> searchRequests = new ArrayList<>();

        // 向量检索
        searchRequests.add(buildDenseSearchReq(queryVector, topK * 2));

        // BM25检索
        if (options.isEnableBm25()) {
            searchRequests.add(buildSparseSearchReq(query, topK * 2));
        }

        // 3. 执行混合检索
        HybridSearchReq hybridReq = HybridSearchReq.builder()
                .collectionName(options.getCollectionName())
                .searchRequests(searchRequests)
                .ranker(new RRFRanker(options.getRrfK()))
                .topK(topK)
                .build();

        SearchResults results = client.hybridSearch(hybridReq);

        // 4. 转换为Spring AI的Document格式
        return convertToDocuments(results);
    }

    // ... 其他方法实现
}
```

## 小结

这篇讲了混合检索的核心内容：

1. **纯向量检索的短板**：语义理解强，但对精确关键词不敏感，容易丢失类名、方法名、错误码等具体信息

2. **BM25 关键词检索**：擅长精确匹配，通过词频、逆文档频率、文档长度三个因素计算相关性

3. **混合检索原理**：同时跑向量检索和关键词检索，用 RRF 算法融合排名，取长补短

4. **RRF 融合策略**：只看排名不看分数，避免了分数归一化的各种问题

5. **实战建议**：大多数场景用混合检索最稳，先保证召回覆盖再优化排序精度
