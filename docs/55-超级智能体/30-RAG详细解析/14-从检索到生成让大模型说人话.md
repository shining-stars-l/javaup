# 从检索到生成：让大模型说人话

## 检索只是半程马拉松

前面几篇咱们把检索这块讲透了——文档预处理、分片、向量化、混合检索、重排序，一路下来能拿到高质量的 Top-K 候选内容。

很多人到这一步就觉得大功告成了：检索到了对的内容，大模型自然能给出对的答案嘛。

但实际跑起来，你会发现事情没这么简单。

假设你在搭一个售后服务机器人，用户问：`我的空调买了三个月，制冷效果变差了，还能免费维修吗？`

经过混合检索 + 重排序，Top-1 返回的内容是：

> 家用空调整机保修 6 年，主要零部件保修 6 年。保修期内因产品质量问题导致的故障，免费上门维修。人为损坏或超出保修期的维修需收费。

内容找得很准，完全命中了用户的问题。但你把这个内容和用户问题一起丢给大模型，模型的回答可能是：

> 您好！根据消费者权益保护法，家电产品在三包期内出现性能故障，商家应当免费维修。您的空调购买了三个月，仍在三包期内，可以享受免费维修服务。建议您拨打我们的客服热线 400-xxx-xxxx 预约上门检测。

听起来挺专业的，但问题来了——检索到的内容说的是"6 年保修"，模型却扯到了"三包期"；检索内容里没提客服热线，模型却自己编了一个。

这就是 RAG 系统的**最后一公里问题**：检索只是一半，生成才是最终交付。内容质量再高，如果 Prompt 设计不好，模型照样会给出错误答案。

:::info RAG生成阶段的核心挑战
即使检索到了完全正确的内容，大模型在生成时仍可能：用自身训练知识覆盖检索结果、在检索内容基础上"合理补充"（即编造）细节、把多个文档的信息混淆在一起。Prompt设计的核心任务就是通过明确的约束，让模型"只说检索到的，不多说没有的"。
:::

## 厨师做菜的启发

这个问题让我想起了厨师做菜。

你去菜市场买了最新鲜的食材（检索阶段），但最终菜好不好吃，还得看厨师怎么处理这些食材（生成阶段）。

- **食材选配**：检索返回了 5 个候选内容，哪些该用、哪些该放、怎么搭配，需要精心安排
- **火候控制**：给模型的指令太严格，回答会很生硬；太宽松，模型会自由发挥
- **调味技巧**：回答的语气、格式、详略程度，都需要通过 Prompt 来调控
- **最终摆盘**：回答要有引用、有来源，让用户知道这道"菜"是用什么"食材"做的

一个好厨师，能把普通食材做出惊艳的味道；一个烂厨师，能把顶级食材糟蹋掉。RAG 也是一样——Prompt 设计得好，普通检索结果也能产出高质量答案；Prompt 设计得烂，顶级检索结果也会翻车。

## RAG Prompt 的三段式结构

RAG 场景下的 Prompt 不是随便写一句"请回答用户的问题"就行的。一个设计良好的 RAG Prompt 通常由三段组成：

1. **系统指令（System Prompt）**：告诉模型你是谁、该怎么做、不能做什么
2. **检索上下文（Retrieved Context）**：把检索到的 Top-K 内容喂给模型
3. **用户问题（User Query）**：用户的原始提问

用厨师的比方来说：
- 系统指令 = 厨师手册（你是川菜师傅，要注意麻辣口味，不能放糖）
- 检索上下文 = 今天采购的食材（这是你能用的全部材料）
- 用户问题 = 客人的点单（客人想吃什么）

### 系统指令：给模型立规矩

系统指令是整个 Prompt 的总纲，决定了模型的行为模式。在 RAG 场景下，系统指令最核心的任务是：**让模型只基于检索到的内容回答问题，不要用自己的知识自由发挥**。

给一个可以直接用的模板：

```
你是一名专业的售后服务顾问。你的任务是根据【参考资料】中的信息，准确回答用户的售后问题。

请严格遵守以下规则：
1. 只基于【参考资料】中的内容回答问题，不要使用你自己的知识。
2. 如果【参考资料】中没有足够的信息来回答问题，请明确回答："根据现有资料，暂时无法回答该问题。建议您拨打客服热线 400-xxx-xxxx 获取人工帮助。"
3. 不要编造任何【参考资料】中没有提到的信息，包括时间、费用、流程等具体细节。
4. 回答时请引用参考资料的编号，格式为 [1]、[2] 等，标注在相关句子的末尾。
5. 如果多条参考资料的信息存在冲突，请指出冲突并建议用户以最新的政策为准。
6. 用友好、专业的语气回答，像一个有经验的售后顾问在和客户沟通。
```

逐条拆解一下每条规则的作用：

| 规则 | 作用 | 解决的问题 |
|:-----|:-----|:-----------|
| 规则1：只基于参考资料回答 | 限制模型的知识来源 | 防止模型用自己的知识覆盖检索结果 |
| 规则2：信息不足时明确告知 | 给模型一个"兜底出口" | 不知道就说不知道，不要硬编 |
| 规则3：不要编造具体细节 | 强调数字、时间、费用这些容易被编造的信息 | 防止模型补充"合理但错误"的细节 |
| 规则4：引用参考资料编号 | 让答案可追溯 | 用户能验证答案来源 |
| 规则5：处理信息冲突 | 多个内容说法不一致时，模型不要自己选一个 | 避免张冠李戴 |
| 规则6：语气要求 | 控制回答风格 | 符合售后服务场景 |

### 检索上下文：把食材摆上案板

拿到 Top-K 候选内容之后，怎么组装成上下文喂给模型？推荐的格式是：**每条内容带编号、带来源信息，用明确的分隔符隔开**。

```
【参考资料】

[1] 来源：空调售后政策 | 更新时间：2024-12-01
家用空调整机保修 6 年，主要零部件保修 6 年。保修期内因产品质量问题导致的故障，免费上门维修。人为损坏或超出保修期的维修需收费。

[2] 来源：上门服务标准 | 更新时间：2024-11-15
保修期内上门维修免收上门费和人工费。超出保修期的维修，上门费 50 元，人工费根据维修项目另计。

[3] 来源：维修预约流程 | 更新时间：2024-12-10
用户可通过 APP、小程序或客服热线预约维修。预约成功后，工程师将在 24 小时内联系用户确认上门时间。
```

这个格式有几个设计要点：

- **编号[1][2][3]**：方便模型在回答时引用，也方便后端解析引用关系
- **来源信息**：告诉模型（和用户）这条信息从哪来的
- **更新时间**：当多条内容信息冲突时，模型可以根据时间判断哪条更新
- **明确的分隔符**：用空行隔开每条内容，避免模型把相邻内容混在一起理解

:::tip 检索上下文的格式设计
带编号、来源、更新时间的结构化格式能显著提升生成质量。编号让模型能准确引用，来源让答案可追溯，更新时间帮助模型处理信息冲突，分隔符防止内容混淆。这几个设计要点缺一不可，特别是对准确性要求高的场景。
:::

## 幻觉：模型的"善意谎言"

### 什么是幻觉

幻觉（Hallucination）这个词听起来很学术，意思其实很直白：**模型生成了看起来很合理、读起来很流畅，但实际上是编造的内容**。

打个比方，你问一个新来的客服同事："这款空调的保修期是多久？"他不确定答案，但又不想说"我不知道"，于是自信地回答："两年"。听起来很合理，但实际保修期是六年。这就是幻觉——不是故意骗你，而是"不知道自己不知道"。

大模型的幻觉也是类似的机制。模型在训练时学到了大量的通用知识，当检索到的内容不够用时，它会自动补全——用训练数据里的通用知识填充答案，而且说得非常自信。

### 三种典型的幻觉表现

**1. 篡改事实**

检索内容明确说了 A，模型回答了 B。

```
检索内容：空调保修期 6 年。
模型回答：空调保修期 3 年。
```

这是最严重的一种。模型不是没看到检索内容，而是用自己的常识（大部分电器保修 1-3 年）覆盖了具体规则。

**2. 凭空捏造**

检索内容里没有提到某个信息，模型自己补了一个。

```
检索内容：保修期内免费维修。
模型回答：保修期内免费维修，维修完成后请在服务单上签字确认，工程师会留下保修卡副本。
```

"签字确认"和"保修卡副本"这些细节检索内容里完全没有，是模型根据常识编造的。

**3. 张冠李戴**

把 A 的信息安到 B 的主体上。

```
检索内容1：空调整机保修 6 年。
检索内容2：洗衣机整机保修 3 年。
模型回答：空调整机保修 3 年。
```

模型把两条内容的信息混在一起，生成了一个看起来对但实际上错的答案。

### 幻觉抑制的实用技巧

幻觉不能完全消除（这是大模型的本质特性），但可以通过 Prompt 设计和参数调节大幅降低发生概率。

**技巧1：反复强调知识来源**

```
只基于【参考资料】中的内容回答问题，不要使用你自己的知识。
```

这条指令看起来简单，但效果显著。没有这条指令时，模型会把检索内容当作参考；有了这条指令，模型会把检索内容当作唯一依据。

**技巧2：给兜底出口**

```
如果【参考资料】中没有足够的信息来回答问题，请明确回答：
"根据现有资料，暂时无法回答该问题。建议您拨打客服热线获取人工帮助。"
```

如果不给这个出口，模型会默认"尽力回答"——也就是开始编造。

**技巧3：禁止编造具体细节**

```
不要编造任何【参考资料】中没有提到的信息，包括时间、费用、流程等具体细节。
```

数字、日期、金额是幻觉的重灾区。模型特别喜欢补全这类信息。

**技巧4：要求先引用再回答**

```
回答时请引用参考资料的编号，格式为 [1]、[2] 等，标注在相关句子的末尾。
```

让模型标注引用来源，间接抑制幻觉——因为模型需要为每句话找到对应的内容，找不到就不敢说。

**技巧5：降低 Temperature 参数**

Temperature 控制模型输出的随机程度：

- Temperature = 0：模型几乎总是选择概率最高的词，输出最确定
- Temperature = 0.7：默认值，有一定随机性
- Temperature = 1.0 或更高：输出非常随机

RAG 场景追求的是准确性，不是创造性。建议设置 Temperature = 0 ~ 0.3。

## 代码实战：售后服务机器人

【截图提示：运行售后服务机器人代码，展示用户问答效果】

```java
/**
 * 售后服务机器人 - RAG生成阶段实现
 * 演示Prompt设计、幻觉抑制、引用对齐
 */
@Service
public class AfterSalesRobotService {

    private final ChatClient chatClient;
    private final VectorStore vectorStore;
    private final RerankerService rerankerService;

    /**
     * 系统Prompt模板
     */
    private static final String SYSTEM_PROMPT = """
        你是一名专业的售后服务顾问。你的任务是根据【参考资料】中的信息，准确回答用户的售后问题。

        请严格遵守以下规则：
        1. 只基于【参考资料】中的内容回答问题，不要使用你自己的知识。
        2. 如果【参考资料】中没有足够的信息来回答问题，请明确回答："根据现有资料，暂时无法回答该问题。建议您拨打客服热线 400-xxx-xxxx 获取人工帮助。"
        3. 不要编造任何【参考资料】中没有提到的信息，包括时间、费用、流程等具体细节。
        4. 回答时请引用参考资料的编号，格式为 [1]、[2] 等，标注在相关句子的末尾。
        5. 如果多条参考资料的信息存在冲突，请指出冲突并建议用户以最新的政策为准。
        6. 用友好、专业的语气回答，像一个有经验的售后顾问在和客户沟通。
        """;

    /**
     * 处理用户问题
     */
    public AnswerResponse handleQuestion(String userQuestion) {
        // 1. 检索阶段：混合检索 + 重排序
        List<Document> candidates = vectorStore.similaritySearch(
                SearchRequest.builder()
                        .query(userQuestion)
                        .topK(20)
                        .build()
        );

        List<Document> reranked = rerankerService.rerank(userQuestion, candidates, 5);

        // 2. 上下文组装
        String context = buildContext(reranked);

        // 3. 生成阶段：调用大模型
        String answer = chatClient.prompt()
                .system(SYSTEM_PROMPT)
                .user(buildUserPrompt(context, userQuestion))
                .options(ChatOptions.builder()
                        .temperature(0.1)  // 低温度，减少随机性
                        .build())
                .call()
                .content();

        // 4. 解析引用
        List<Citation> citations = parseCitations(answer, reranked);

        return new AnswerResponse(answer, citations, reranked);
    }

    /**
     * 组装检索上下文
     */
    private String buildContext(List<Document> documents) {
        StringBuilder sb = new StringBuilder("【参考资料】\n\n");

        for (int i = 0; i < documents.size(); i++) {
            Document doc = documents.get(i);
            Map<String, Object> metadata = doc.getMetadata();

            sb.append(String.format("[%d] 来源：%s | 更新时间：%s\n",
                    i + 1,
                    metadata.getOrDefault("source", "未知"),
                    metadata.getOrDefault("update_time", "未知")));
            sb.append(doc.getContent());
            sb.append("\n\n");
        }

        return sb.toString();
    }

    /**
     * 构建用户Prompt
     */
    private String buildUserPrompt(String context, String userQuestion) {
        return context + "【用户问题】\n" + userQuestion;
    }

    /**
     * 解析回答中的引用
     */
    private List<Citation> parseCitations(String answer, List<Document> documents) {
        List<Citation> citations = new ArrayList<>();
        Pattern pattern = Pattern.compile("\\[(\\d+)]");
        Matcher matcher = pattern.matcher(answer);

        Set<Integer> citedIndexes = new HashSet<>();
        while (matcher.find()) {
            int index = Integer.parseInt(matcher.group(1));
            citedIndexes.add(index);
        }

        for (Integer index : citedIndexes) {
            if (index > 0 && index <= documents.size()) {
                Document doc = documents.get(index - 1);
                citations.add(new Citation(
                        index,
                        doc.getContent(),
                        (String) doc.getMetadata().get("source")
                ));
            }
        }

        return citations;
    }

    /**
     * 回答响应
     */
    @Data
    @AllArgsConstructor
    public static class AnswerResponse {
        private String answer;              // 模型回答
        private List<Citation> citations;   // 引用列表
        private List<Document> sources;     // 原始检索结果
    }

    /**
     * 引用信息
     */
    @Data
    @AllArgsConstructor
    public static class Citation {
        private int index;      // 引用编号
        private String content; // 被引用内容
        private String source;  // 来源
    }
}
```

## 兜底回答的艺术

兜底回答是幻觉抑制的最后一道防线。当检索结果不足以回答用户问题时，模型应该给出一个诚实的"不知道"。

但"不知道"也有讲究。直接回答"我不知道"会让用户觉得这个系统没用。好的兜底回答应该做到三点：

1. 承认信息不足
2. 给出替代方案（如联系人工客服）
3. 如果能部分回答，先给出已知的部分

几种兜底模板：

**完全无法回答**：
```
根据现有资料，暂时无法回答该问题。建议您拨打客服热线 400-xxx-xxxx 获取人工帮助。
```

**部分可以回答**：
```
关于保修期的问题，您的空调在 6 年保修期内可以免费维修 [1]。
但关于具体的维修时长，现有资料中没有相关说明，建议您预约维修时和工程师确认。
```

**问题超出范围**：
```
这个问题超出了我的服务范围。我主要负责解答产品售后、维修保养等问题。
如果您有这方面的疑问，随时可以问我。
```

## 上下文窗口的限制与应对

大模型的上下文窗口是有限的。虽然现在很多模型支持 128K 甚至更长的上下文，但塞太多内容进去并不是好事：

| 问题 | 表现 |
|:-----|:-----|
| 关键信息被稀释 | 内容越多，噪音越大，模型越容易被不相关的内容干扰 |
| 迷失在中间（Lost in the Middle） | 研究表明，模型对中间位置的信息关注度较低 |
| 成本增加 | 输入 token 越多，API 费用越高，响应延迟也越大 |

### 经验法则

| 场景 | 推荐内容条数 | 理由 |
|:-----|:-------------|:-----|
| 简单事实问答 | 3~5 条 | 答案通常在 1~2 条里，多给几条做补充 |
| 复杂问题 | 5~8 条 | 需要综合多条信息 |
| 总结类问题 | 8~10 条 | 需要覆盖更多内容，但要注意去重 |

如果你用了重排序（Reranker），Top-K 的质量已经很高了，通常 3~5 条就够用。**宁可少给几条高质量的，也不要多给一堆低质量的**。

:::caution 避免"迷失在中间"效应
研究表明大模型对输入内容的关注度呈"U形"：开头和结尾的内容被充分关注，中间部分容易被忽略（"Lost in the Middle"效应）。因此：不要堆砌大量上下文，重要内容放在开头或结尾，宁可少给高质量的，不要多给低质量的。
:::

## 常见 Prompt 设计误区

### 误区1：太短，没有约束

```
你是一个客服助手，请回答用户的问题。
```

这种 Prompt 等于没有约束。模型会用自己的知识自由发挥，检索到的内容只是参考。

:::warning 常见Prompt误区
**误区1：System Prompt太短**——没有明确的知识边界约束，模型会自由发挥。**误区2：指令太多互相冲突**——超过8条规则容易出现矛盾，如"要详细"和"要简洁"同时出现。**误区3：没有兜底指令**——不告诉模型"不知道怎么办"，它就会编造。**误区4：不要求引用**——缺少引用要求，模型更容易产生幻觉且无法追溯。
:::

### 误区2：太长，指令冲突

有些团队恨不得把所有能想到的规则都塞进去，写了几十条指令。结果指令之间互相矛盾——比如一条说"回答要详细"，另一条说"回答要简洁"。

**经验法则**：System Prompt 控制在 5~8 条核心规则，每条规则聚焦一个明确的行为约束。

### 误区3：没有兜底指令

如果不告诉模型"不知道的时候该怎么办"，它会默认"尽力回答"——也就是开始编造。兜底指令是抑制幻觉最关键的一条，不能省。

### 误区4：忽略引用要求

不要求模型标注引用，有两个坏处：
1. 用户无法验证答案的来源
2. 模型更容易编造（因为不需要为每句话找依据）

## 生成参数调优

除了 Prompt 设计，大模型的生成参数也会影响答案质量：

| 参数 | 推荐值 | 说明 |
|:-----|:-------|:-----|
| temperature | 0 ~ 0.3 | 低温度让模型更保守、更准确 |
| top_p | 0.9 ~ 0.95 | 配合低温度使用 |
| max_tokens | 根据场景设置 | 避免回答被截断 |

**注意**：temperature 和 top_p 通常不需要同时调。大多数情况下，只设置 temperature 就够了。

## 小结

这篇讲了 RAG 生成阶段的核心内容：

1. **检索只是一半**：内容质量再高，Prompt 设计不好照样翻车

2. **三段式 Prompt 结构**：系统指令定规矩、检索上下文给食材、用户问题是点单

3. **幻觉抑制技巧**：限定知识来源、给兜底出口、禁止编造细节、要求引用、降低温度

4. **引用对齐**：让答案可追溯，用户能验证

5. **上下文管理**：宁可少给高质量的，不要多给低质量的
