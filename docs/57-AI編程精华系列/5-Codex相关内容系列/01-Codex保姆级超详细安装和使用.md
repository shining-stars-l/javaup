# Codex超级详细的保姆级安装和使用

很多小伙伴第一次用 Codex，会把注意力全放在“怎么下载”和“按钮在哪”。软件确实几分钟就能装好，真正影响体验的却是后面几件事：打开哪个目录、给多大权限、怎样描述任务、怎么检查改动，以及什么时候该让它停下来问你。

我把这篇教程设计成了一次完整上手。我们会从空白环境开始，最后让 Codex 接手一个小项目，并把结果交付到可以检查、可以运行、可以撤销的状态。第一次使用的小伙伴可以从头跟着做，已经装好的小伙伴也可以直接跳到“第一次完整交付”。

### 注意
Codex 更新很快，如果你看到的按钮位置略有不同，先找同名功能，再到文末的官方文档确认最新入口。额度、模型名单、上下文数字这类信息经常变化。

:::info 读完以后，你应该能独立完成这些事

- 安装桌面端或 Codex CLI，并判断自己更适合哪种入口；
- 使用 ChatGPT 账号或 API Key 登录，知道两种计费与能力边界；
- 给 Codex 划定工作目录，选对权限模式；
- 用“目标、现场、边界、验收”四部分交代一个需求；
- 检查 `git diff`，运行验证，拒绝只看一句“已经完成”；
- 用 `AGENTS.md` 固化项目规则，分清 Skill、Plugin 与 MCP；
- 处理命令找不到、登录失败、权限卡住、上下文变乱等常见问题。
:::

## 先选入口：桌面端、CLI、IDE还是云端

Codex 现在可以出现在好几个地方。底层能力相通，操作方式和使用场景有区别。

| 入口 | 更适合谁 | 优点 | 需要适应的地方 |
| --- | --- | --- | --- |
| ChatGPT 桌面端里的 Codex | 刚接触 AI 编程、喜欢可视化界面、还要处理文档和图片的小伙伴 | 项目、对话、终端、浏览器和文件预览都在一个窗口里 | 界面功能多，第一次容易把聊天、工作和 Codex 模式混在一起 |
| Codex CLI | 熟悉终端、经常在代码仓库里工作、需要脚本化的开发者 | 启动快，贴近 Git、测试和构建流程，也能用 `codex exec` 做自动化 | 需要认识终端、工作目录和几个常用命令 |
| IDE 扩展 | 希望边看源码边与 Codex 协作的开发者 | 文件、代码选区和诊断信息离编辑器更近 | 会同时出现 IDE 自己的功能和 Codex 功能 |
| Codex Cloud | 需要把任务放到云端环境并行执行的团队 | 本机不用一直占着，可以处理多个任务 | 要先配置仓库和云端环境，权限边界也不同 |

我建议第一次使用先选桌面端或 CLI。桌面端比较直观，CLI 更容易理解 Codex 到底在哪个目录工作、执行了什么命令。本文两条路线都会讲，后面的任务方法可以通用。

## 安装前准备：先把这四件事确认好

### 1. 准备可用的登录方式

本地使用支持两种方式：

- **使用 ChatGPT 账号登录**：Codex 使用量跟随你的 ChatGPT 套餐和工作区规则；
- **使用 OpenAI API Key 登录**：按 API 账户的标准用量计费，部分依赖 ChatGPT 工作区或云端服务的能力可能不可用。

个人日常使用一般先选 ChatGPT 登录。API Key 更适合私有脚本、CI 或需要单独核算 API 成本的环境。

:::danger API Key别这样保存
不要把 Key 写进 `AGENTS.md`、项目源码、截图、聊天记录或 Git 提交。需要给命令使用时，放进环境变量或团队认可的密钥管理系统。Codex 的 `~/.codex/auth.json` 也可能包含凭据，不能上传到仓库。
:::

### 2. 准备一个练习目录

别拿桌面根目录、下载目录或整个个人文件夹做第一次练习。范围太大时，Codex 需要面对大量无关文件，你自己也很难确认它改了什么。

可以新建一个独立目录：

```bash
mkdir camping-gear-ledger
cd camping-gear-ledger
git init
```

这个练习项目准备做一个“露营装备借还台账”：记录帐篷、营灯和折叠椅的借出状态，支持按归还日期筛选。场景够小，又能走完页面开发、数据校验和验收流程。

这里先初始化 Git。Git 相当于给文件变化建立档案。即使你还不会分支和合并，至少也能通过 `git status` 和 `git diff` 看清变化。

### 3. 确认项目自己能运行

如果你要让 Codex 修改现有项目，先手动执行一次项目常用命令，例如：

```bash
npm install
npm test
npm run build
```

Java 项目可能是：

```bash
./mvnw test
```

命令要按项目实际情况选择。提前跑一次的目的是有必要的：你需要知道基线是否正常。项目原本就有 17 个失败测试，任务结束后还看到 17 个，含义跟“Codex 新改坏了 17 个测试”完全不同。

### 4. 记录已有改动

进入现有仓库后先执行：

```bash
git status --short
```

如果输出不为空，先弄清哪些文件是自己正在做的。让 Codex 工作时明确告诉它保留这些改动。条件允许的话，先提交一个检查点或新建分支。

## 路线二：安装Codex CLI

CLI 适合希望在终端里直接读代码、改文件、跑命令的小伙伴。下面优先使用官方当前推荐的安装方式。

### macOS和Linux：使用独立安装脚本

在终端执行：

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

脚本完成后关闭并重新打开终端，再检查版本：

```bash
codex --version
```

如果仍然提示 `command not found`，先看安装结束时有没有给出 PATH 提示。终端只会从 PATH 记录的目录里寻找命令，文件已经下载不代表当前 Shell 一定能找到它。

### 已经有Node.js：也可以使用npm

官方保留了 npm 安装入口：

```bash
npm install -g @openai/codex
```

然后执行：

```bash
codex --version
```

如果 npm 报全局目录没有权限，别顺手给整段命令加 `sudo`。优先修正 Node 的安装方式或 npm 全局目录权限，避免后面更新时出现一部分文件属于 root、一部分属于当前用户的情况。

### Windows怎么选

Windows 可以按 [Codex CLI官方快速开始](https://learn.chatgpt.com/docs/codex/cli#getting-started) 的 Windows 标签安装。已有 WSL2 开发环境的小伙伴，也可以在 WSL2 里按 Linux 路线使用。项目依赖、Git 和 Codex 尽量放在同一个环境里，少走“命令在 Windows，代码在 WSL，依赖又装在另一边”的弯路。

### 第一次启动和登录

进入练习目录再启动：

```bash
cd camping-gear-ledger
codex
```

首次启动会让你选择登录方式。使用 ChatGPT 登录时，终端会打开浏览器；完成账号验证后回到终端即可。也可以单独执行：

```bash
codex login
```

登录以后先输入：

```text
/status
```

重点确认当前目录、模型、权限策略、可写范围和上下文余量。这里的信息比“界面看起来登录成功了”更有用。

### 更新Codex

使用独立安装脚本的环境，可以重新执行同一条官方脚本完成更新：

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

当前版本也提供：

```bash
codex update
```

这个命令只在安装方式支持自更新时生效。如果它提示不支持，就沿用当初的安装方式更新。npm 安装则重新执行 `npm install -g @openai/codex`。

更新以后再跑 `codex --version`。碰到配置、认证、Git 或运行时异常时，可以用 `codex doctor` 生成诊断信息。提交诊断截图前仍要检查里面是否带有本机路径或其他敏感信息。

## 权限怎么选：第一次不要电脑的完整权限交给 Codex

Codex 的权限由两部分共同决定：

- **Sandbox** 决定它能访问哪些文件、网络和系统资源；
- **Approvals** 决定碰到边界动作时，由谁审核、什么时候暂停。

桌面端和 CLI 的文案可能略有不同，当前常见模式可以这样理解：

| 模式 | Codex可以做什么 | 适合场景 | 我给新手的建议 |
| --- | --- | --- | --- |
| Ask for approval | 能在当前工作区读写和执行日常命令，越过边界前找你确认 | 第一次上手、陌生仓库、包含重要文件的项目 | **从这里开始** |
| Approve for me / Auto-review | 工作区边界不变，额外访问请求交给自动审核 | 已经清楚项目风险，希望减少频繁确认 | 先做几轮低风险任务再用 |
| Full access | 可以访问更广的本机文件和网络，通常不会逐项等你批准 | 外层已经有隔离环境，且任务确实需要广泛权限 | 不要拿真实个人目录练手 |
| Read-only | 只能读取和分析，修改或执行受限制 | 代码审计、方案评估、初次了解仓库 | 很适合“先看再决定” |

Auto-review 改变的是“谁来审核越界请求”，不会自动扩大 Sandbox。Full access 才会明显放大范围，同时增加误删、泄露和意外执行的风险。

CLI 中输入下面的命令可以查看或切换：

```text
/permissions
```

:::warning 流程图占位（暂不绘制）：权限请求如何被处理
建议画出“模型提出动作 → Sandbox判断是否在边界内 → 边界内直接执行 / 边界外进入Approval → 用户或Auto-review审核 → 执行或拒绝”的流程。图中要把 Sandbox 和 Approval 分成两层，避免让读者误以为自动审核等于完全放权。
:::

## 第一次完整交付：做一个露营装备借还台账

这一节不追求页面多炫，重点是把“需求交代、计划确认、执行、验证、审核”完整跑一遍。桌面端直接在对话框输入，CLI 在终端界面输入，方法相同。

### 第一次对话只做现场调查

先发送下面这段：

```text
请先检查当前目录和Git状态，不要修改任何文件。

我准备做一个露营装备借还台账，供8到12人的小团队使用。
请根据当前目录里的实际内容告诉我：
1. 这里是不是一个可以开始开发的项目；
2. 已经有什么技术栈、脚本和项目规则；
3. 开始实现前还缺哪些关键决定；
4. 你准备怎样验证最终结果。

如果目录是空的，请给出两个轻量方案并说明区别，先等我选择。
```

这段话有三个作用：限制它暂时不改文件，让它引用真实现场，还给技术选型留了确认点。空目录里直接说“做个系统”，Codex 可能替你决定框架、包管理器和页面结构。选择本身未必错，但你很难知道这些依赖是怎么进来的。

### 确认方案以后再执行

假设我们选择“Vite + TypeScript 的纯前端项目”，下一轮可以这样说：

```text
按Vite + TypeScript方案实现，可以开始修改。

业务要求：
- 默认展示帐篷、营灯、折叠椅三类装备；
- 每条记录包含借用人、借出日期、计划归还日期和当前状态；
- 可以按“借出中、已归还、已逾期”筛选；
- 计划归还日期早于今天、并且还没归还时，状态自动显示为已逾期；
- 先用本地模拟数据，不接后端接口。

边界：
- 保留已有文件和未提交改动；
- 不引入重量级UI组件库；
- 不发布到公网；
- 不替我提交Git。

验收：
- 运行项目已有的格式检查、测试和构建；
- 至少补上“跨月逾期”和“当天归还”两个日期边界测试；
- 检查375px宽度下没有横向滚动；
- 完成后列出修改文件、验证命令、验证结果和仍未覆盖的风险。
```

这段任务里有目标，也有业务规则、禁止项和验收证据。Codex 可以自己决定实现细节，又不会把“做完了”的标准理解成只生成几个文件。

### 执行过程中看什么

Codex 工作时，你不需要盯住每一行输出，下面几类动作要多看一眼：

1. **安装依赖**：确认包名和用途，陌生脚本先看来源；
2. **删除、覆盖和移动文件**：检查目标路径有没有扩大；
3. **访问网络或工作区外目录**：想一想任务是否真的需要；
4. **跳过测试**：看它给出的原因是环境问题，还是为了赶快结束；
5. **需求理解发生变化**：例如它发现日期状态来自后端，就该重新确认方案。

你随时可以补充方向。例如：

```text
筛选逻辑保留。卡片不要继续加阴影，把层级改成边框和留白。
先修移动端横向滚动，再继续做其他细节。
```

这种反馈比“再高级一点”“不够好看”更容易落到具体修改上。

### 任务结束后别急着说通过

先在 Codex 里看变化：

```text
/diff
```

也可以在普通终端执行：

```bash
git status --short
git diff --stat
git diff
```

然后复跑它声称已经通过的命令。页面类项目还要打开真实页面，检查桌面端、移动端、筛选交互和控制台错误。报告里写着“响应式正常”，无法代替 375px 视口下的实际画面。

CLI 还可以输入：

```text
/review
```

让 Codex 对当前工作区再做一次专门审查。审查适合找遗漏，最终是否接受仍由 diff、测试和运行结果决定。

:::warning 截图提示：一次完整任务的改动审核
放一张审核面板或 `/diff` 截图，能看到文件列表和某个具体代码块的增删。不要只截“任务完成”四个字。
:::

:::warning 流程图占位（暂不绘制）：从打开目录到可验收交付
建议画成七个节点：“确认目录与Git基线 → 只读调查 → 确认方案 → 设置权限边界 → 实施与阶段反馈 → 测试和运行验证 → 审核diff并决定接受或回退”。在“发现范围变化”和“验证失败”处各画一条回到前面步骤的支线。
:::

## 提示词不需要太长，把四件事说清楚就可以

我给工程任务常用的结构是：**目标、现场、边界、验收**。

### 目标：最终要发生什么变化

“优化一下订单页”范围太大。可以改成：

> 订单列表在连续点击刷新时会出现重复记录，请定位原因，补复现测试并修复。修复后重复响应不能覆盖较新的列表数据。

### 现场：给出可核对的线索

把报错、复现步骤、相关目录、最近变更或设计稿位置告诉它：

> 问题出现在 `admin-web`，Chrome 中连续点击三次刷新可以复现。接口返回都是 200，第三次请求最先回来。先从请求竞态和状态合并逻辑查起。

### 边界：哪些事情不能顺手做

例如：

- 不改后端接口和数据库结构；
- 保留我在 `OrderTable.tsx` 里的未提交改动；
- 不升级整个依赖树；
- 不创建远程分支，不发布，不推送；
- 如果修复需要改变产品行为，先停下来问我。

### 验收：拿什么证明完成

例如：

- 新测试可以在修复前失败、修复后通过；
- 原有订单列表测试仍通过；
- 快速刷新只展示最新一次请求对应的数据；
- 给出测试命令和关键结果；
- 说明竞态修复覆盖了哪些路径，哪些异常还没覆盖。

:::tip 一个可以重复使用的任务模板

```text
目标：
[说清最终要改变的行为]

现场：
[项目目录、复现步骤、报错、相关线索、已有改动]

边界：
[禁止修改的内容、需要保留的内容、必须确认的决定]

验收：
[测试、构建、页面、接口、日志或数据方面的证据]

先检查现场。如果我的描述与仓库实际情况冲突，以现场证据指出冲突，先不要猜着改。
```
:::

## 用AGENTS.md把项目规矩交代清楚

同一套约定每次都粘贴，既浪费上下文，也容易漏掉。Codex 会在开始工作前读取 `AGENTS.md`，我们可以把长期有效的项目规则放进去。

一个适合练习项目的版本可以这样写：

```markdown
# AGENTS.md

## 项目定位

- 这是露营装备借还台账的前端项目。
- 当前数据来自本地模拟，除非任务明确要求，不要接入远程服务。

## 开发约定

- 使用现有包管理器，不要混用 npm、pnpm 和 yarn。
- 日期计算集中放在 `src/domain/loanStatus.ts`，组件只负责展示。
- 新增日期规则时必须补边界测试。
- 不要把测试时间直接写成 `new Date()`，使用可注入的当前日期。

## 验证

- 修改 TypeScript 后运行 `npm run lint` 和 `npm test`。
- 修改构建配置或依赖后额外运行 `npm run build`。
- 页面改动检查 375px 与 1280px 两个宽度。

## 安全边界

- 不自动提交、推送或发布。
- 不删除用户已有文件；确实需要删除时先解释目标和原因。
- 不在日志、示例数据或截图中写真实姓名和联系方式。
```

规则要具体，还要能执行。“代码要优雅”“注意安全”很难指导下一步。写清测试命令、目录边界和需要确认的动作，效果会稳定很多。

### 多层AGENTS.md怎样生效

Codex 会从全局到当前工作目录逐层发现规则：

1. 默认从 `~/.codex/AGENTS.md` 读取个人通用约定；
2. 从 Git 根目录开始，沿目录向当前工作目录查找项目级文件；
3. 同一目录存在 `AGENTS.override.md` 时，它优先于 `AGENTS.md`；
4. 离当前目录越近的规则越靠后，发生冲突时有更高优先级；
5. 规则链存在大小限制，别把整套项目文档都塞进去。

全局文件适合放语言偏好、通用安全边界。项目根目录适合放构建、测试、架构与提交规则。某个服务有特殊约定，再在它的目录里补一层。

放一张 `/init` 生成文件，或 Codex 汇报当前规则来源的截图。截图里同时展示项目根目录和嵌套目录会更容易理解优先级。
:::

建议用目录树表现“全局 `~/.codex/AGENTS.md` → 仓库根 `AGENTS.md` → 子目录 `AGENTS.override.md` → 当前任务”，并在旁边标注“越接近当前目录，规则越具体”。

## Skills、Plugins和MCP分别解决什么问题

这三个词经常一起出现，我用“缺的到底是什么”来判断。

| 机制 | 给Codex补充什么 | 适合例子 |
| --- | --- | --- |
| Skill | 一套可复用的步骤、模板和参考资料 | 每次发布前都按同一清单检查文档链接、构建和截图 |
| Plugin | 可安装、可分享的一组能力，里面可以带 Skills、连接器或两者 | 安装一个团队插件，同时获得周报流程和 GitHub 工具 |
| MCP | 外部工具和数据连接 | 读取监控告警、查询设计系统、访问内部工单平台 |
| AGENTS.md | 进入某个项目就长期生效的本地约定 | 这个仓库用什么命令测试，哪些目录禁止修改 |

### Skill怎么用

当请求与某个 Skill 匹配时，Codex 可以自动选择；也可以显式写 `$技能名`。例如团队有一个 `release-check` Skill：

```text
$release-check 检查当前分支能不能发布，只做检查，不要提交或部署。
```

Skill 很适合已经跑通、以后还要反复执行的流程。第一次做任务时先把流程磨顺，确认输入、步骤和输出，再用 `$skill-creator` 封装。这样生成的是你真实会用的工作方法，不是一份看起来完整、实际没走过的说明书。

安装社区 Skill 前先读 `SKILL.md` 和配套脚本，尤其检查下载、上传、安装软件、读取凭据、删除文件等动作。知名仓库也要看当前版本，不能只凭名称判断安全。

### Plugin怎么用

Plugin 是安装和分发单位，可以同时装进工作流和外部工具。你可以在桌面端或 `/plugins` 中查看可用项。安装后，先看它包含哪些 Skill、连接器和权限，再决定是否授权账号。

涉及发布、发消息、改工单、操作云资源的 Plugin 可能产生外部影响。第一次使用先做读取或预览，确认目标账号、项目和权限范围，再执行写操作。

### MCP什么时候值得接

如果任务必须访问 Codex 当前工具之外的服务，MCP 才有价值。例如要根据真实告警修复线上问题，需要读取监控平台；要核对接口契约，需要访问团队的 API 文档服务。

CLI 可以从这里开始：

```bash
codex mcp --help
```

先看当前版本支持的 `list`、`add`、`remove` 和登录参数，再照目标服务的官方接入说明配置。别把网上某个过时的一行命令当成所有环境都通用的安装办法。

放一张当前版本的 Skills/Plugins 页面，标出已安装、来源、权限或连接状态。账号名称和组织信息需要打码。
:::

中心放 Codex，四周分别连接 `AGENTS.md`、Skill、Plugin、MCP。每条边只写一个职责：项目约定、重复流程、安装分发、外部工具。Plugin内部再画出可包含 Skill 与连接器，避免把四个概念画成平级同义词。

## 桌面端还能做什么：从文件整理到浏览器验收

桌面端还可以处理不少代码之外的任务。它能把文件、终端、浏览器、桌面应用和 Plugin 放进同一段任务里。小伙伴刚开始最好把这些能力拆开练，每次只增加一个外部工具。这样出了问题，容易判断是提示写偏了、权限不够，还是工具本身没有连接好。

### 做文件任务时，先报告再整理

假设你有一批会议录音、字幕和海报素材，文件名比较乱。别直接让 Codex“整理一下并删除重复文件”。删除标准、重复判定和目标目录都没说，风险太高。

可以先发一个只读任务：

```text
只检查当前素材目录，不要移动、重命名或删除文件。

请按扩展名、文件大小和修改时间生成清单，找出：
1. 大于500MB的文件；
2. 文件名相似但内容是否重复还无法确认的文件；
3. 没有对应字幕的录音；
4. 可能属于临时导出物的文件。

报告写到reports/material-audit.md。
任何删除建议都要写出原路径、判断依据和预计释放空间。
```

看完报告，再让它把确认过的文件移动到一个新建的归档目录。真要删除时，优先移到系统废纸篓或项目内的待清理目录，保留恢复机会。

:::warning 截图提示：文件审计报告与权限确认
建议放两张图：一张展示 Codex 生成的文件清单，一张展示移动或删除前的权限确认。个人路径、客户名称和文件内容要打码。
:::

### 让浏览器参与页面验收

页面开发最常见的误区，是代码写完、构建通过就结束。桌面端可以让 Codex 打开本地页面，检查布局、交互和控制台信息。任务要给出网址、视口和操作路径：

```text
启动当前前端项目，用浏览器检查以下流程：
1. 在1280×800下打开装备列表；
2. 筛选“已逾期”，确认只剩逾期记录；
3. 切换到375×812，检查表格、筛选区和弹窗是否横向溢出；
4. 查看控制台是否有错误；
5. 保存两种宽度的验收截图，并列出发现的问题。

先不要修改代码。我确认问题清单以后再修。
```

这段任务把“发现问题”和“修代码”分成两轮。第一轮的截图与问题清单可以当基线，第二轮修完后再走一遍同样路径，前后对比会很清楚。

如果网页需要登录，优先使用你已经确认过的测试账号和测试环境。生产后台里可能有真实订单、客户数据和删除按钮，不能因为浏览器已经登录就默认允许操作。

:::warning 截图提示：浏览器验收与页面批注
放一张本地页面验收截图，标出视口尺寸、控制台状态和问题批注。截图使用模拟数据，不要出现真实手机号、地址或Token。
:::

### 需要登录态时，再考虑连接日常浏览器

普通内置浏览器适合公开网页和本地站点。任务必须访问登录后的系统时，可以按当前版本的官方指引连接 Chrome 等浏览器。连接以后，Codex 可能看到已登录页面中的数据，权限范围要收紧：

- 新开独立标签页，别接管你正在填写的页面；
- 只开放任务需要的域名；
- 查询与下载可以先做，提交、发布、删除和付款要单独确认；
- 任务结束检查新建标签页、下载文件和外部系统状态；
- 不要让网页里的文字改变原任务边界，网页内容也可能包含诱导 Agent 操作的提示。

可以把边界直接写进任务：

```text
打开测试环境的内容后台，读取最近7天处于“待审核”的文章列表。
只生成标题、作者、提交时间和风险提示的报告。
不要点击通过、驳回、发布、删除，也不要给作者发消息。
如果页面要求额外授权，停下来告诉我。
```

### 文档、表格和演示稿也要走验收

当前安装中如果有 Documents、Spreadsheets、Presentations 一类 Plugin，Codex 可以创建或修改相应文件。这里仍然遵循“输入、处理、输出、验收”的思路。

例如整理一份露营装备盘点表，可以这样交代：

```text
读取inventory-raw.xlsx，新生成inventory-cleaned.xlsx，保留原文件不动。

处理要求：
- 统一装备编号格式为CG-四位数字；
- 标出借用人为空、归还日期早于借出日期的行；
- 增加“数据问题”列，不要猜测或自动修复异常值；
- 新建“汇总”工作表，按装备类型统计总数、借出中和已逾期数量；
- 完成后检查公式、筛选范围、日期格式和中文显示。
```

这类任务最怕悄悄改原件，所以要明确“新生成一份”。交付时打开生成文件，检查公式引用、分页、文字截断和乱码。文件能成功保存，只能说明格式可写，不能说明内容已经正确。

### 图像生成要把用途和限制写进去

如果当前环境安装了图像生成 Skill，可以显式选择它。比如给“社区旧物修复日”做一张活动插画：

```text
$imagegen 生成一张16:9活动头图，用于社区旧物修复日的网站首页。

画面内容：木工桌上放着被修好的收音机、台灯和帆布包，三位邻居在交换工具。
视觉要求：温暖的编辑插画，米白背景，砖红和墨绿为主色，留出左侧标题区。
限制：图片里不要生成文字，不要出现品牌Logo，不使用真人照片。
输出：提供1920×1080 PNG，并说明标题文字适合放在哪个安全区域。
```

生成以后要看手指、工具结构、品牌元素、留白和裁切。图片任务通常比文字问答消耗更多资源，复杂需求先出一张方向稿，确认构图后再做变体。

## 模型、个性、配置与记忆怎样分工

把所有偏好都写进同一个地方，后面很容易乱。模型选择、说话风格、工程规则、会话上下文和长期记忆各管一层。

| 信息 | 更合适的位置 | 例子 |
| --- | --- | --- |
| 本轮需要多少推理、使用哪个可用模型 | `/model` 或界面模型选择 | 简单改文案用较轻配置，大型重构提高推理强度 |
| 回答的语气与表达习惯 | 个性化设置或 `/personality` | 中文回答，解释时先给结论 |
| 所有项目通用的工作约定 | `~/.codex/AGENTS.md` | 修改文件前检查 Git 状态 |
| 当前仓库的构建与安全规则 | 项目内 `AGENTS.md` | Java 21、运行哪个测试、禁止改历史迁移 |
| 某一轮任务的目标和现场 | 当前对话 | 修复这次订单竞态，保留指定文件改动 |
| 可跨会话召回的经验 | Memories，可用时再开启 | 某个仓库长期采用的发布习惯 |

### 模型和推理强度按任务选

当前可用模型会随套餐、工作区和版本变化，在 `/model` 或界面里看实时列表。模型越强、推理越深，通常花费的时间和用量也越高。改一个配置文案、找一个类名，没必要始终开最高强度；跨模块重构、复杂故障和架构审查可以给更多推理空间。

模型切换不会自动修正模糊需求。任务边界不清楚时，换更强模型仍可能很认真地做错方向。

### config.toml适合稳定的本机配置

CLI 的主要用户配置默认放在 `~/.codex/config.toml`。第一次使用不需要马上改它，默认设置已经能启动。等你知道某个选项解决什么问题，再做小范围配置。

例如把 CLI 凭据优先存进系统钥匙串，并让 Codex 在任务运行时尽量阻止电脑睡眠：

```toml
cli_auth_credentials_store = "keyring"
check_for_update_on_startup = true

[features]
prevent_idle_sleep = true
```

配置字段会演进。修改前查 [Config Reference](https://learn.chatgpt.com/docs/config-file/config-reference)，改完重启 Codex，用 `/status` 或 `codex doctor` 确认生效。不要从旧教程整段复制一份配置，更不要在不了解含义时打开 `danger-full-access` 或绕过审批的选项。

### Memories可用时，把它当辅助线索

部分版本和工作区会提供 Memories。CLI 的官方配置参考目前把该特性列为可选功能，默认可能未开启。它会从历史任务里整理可能有用的经验，并在相关会话中召回。

记忆适合保存稳定偏好和经过验证的项目经验，下面这些内容不适合交给它兜底：

- 当天才变更的线上状态；
- API Key、账号、客户数据等敏感信息；
- 必须强制执行的安全规则；
- 只在本次需求有效的临时决定；
- 没有验证过的错误猜测。

强制规则写进 `AGENTS.md`、权限或 CI；当前事实重新从源码、日志和外部系统核对。记忆能省掉重复介绍，不能替你证明今天的项目仍然和上周一样。

:::warning 结构图占位（暂不绘制）：五层上下文与规则来源
建议从内到外画“本轮任务 → 会话上下文 → 项目 `AGENTS.md` → 全局个性与规则 → 可选 Memories”，旁边单独放“模型与推理配置”。用箭头说明磁盘、Git、测试和外部系统仍是当前事实来源。
:::

## 长任务怎样保持清醒

同一个对话持续太久，需求、日志、代码片段和工具结果都会进入上下文。内容越多，早期限制越可能只剩摘要，模型也更难判断哪段信息仍然有效。

我通常这样控制：

1. 一个会话只围绕一类目标，例如“修复订单竞态”，别中途又做首页改版；
2. 大段日志先让 Codex提取错误链和关键时间线，不要反复粘贴全文；
3. 每完成一个阶段，让它记录决定、改动、验证和待办；
4. 用 `/status` 看上下文状态；
5. 阶段边界使用 `/compact`，压缩后检查关键约束有没有保留；
6. 新目标用 `/new`，同一目标的替代方案用 `/fork`；
7. 隔天继续时用 `codex resume`，先让它重新核对工作区现状。

恢复旧会话时，磁盘和 Git 状态可能已经变了。第一句话可以写：

```text
继续上次任务前，先重新检查git status、当前分支和相关文件。
把磁盘现状与上次结论做对比，有冲突就先列出来，不要直接覆盖。
```

上下文压缩保存的是任务摘要，无法替代源码、Git 和测试这些当前证据。

## 代码审核与Git：把回退路线留好

### 开始前留一个检查点

现有项目在任务开始前保持清晰的 Git 状态最省心。你可以先提交自己的工作，或至少记下未提交文件。Codex 的任务范围越明确，后面越容易判断哪些改动属于它。

### 完成后分三层检查

**第一层看范围**：

```bash
git status --short
git diff --stat
```

有没有无关文件、锁文件异常膨胀、构建产物或本地配置被带进来？

**第二层看内容**：

```bash
git diff
```

检查核心逻辑、异常分支、敏感信息和测试质量。不要因为 diff 很长就直接“全部暂存”。AI 生成的代码同样需要代码审查。

**第三层看行为**：

运行测试、构建、页面、接口或日志验证。不同项目的证据不同，编译成功也不等于业务行为正确。

### Worktree适合并行任务

Git Worktree 可以让多个任务在同一仓库的不同工作目录里进行。它适合“一个 Agent 改筛选，一个 Agent 查性能”这类低耦合任务。两个任务同时碰同一个核心文件，最后仍然会遇到合并冲突。

第一次使用 Worktree 前先理解分支归属和目录位置。它提供隔离，不会自动消除需求冲突、共享数据库影响或外部服务写入。

放一张创建新对话时选择 Worktree 的截图，并标出原工作区与新工作树的区别。
:::

## 自动化和远程控制：先手动跑通，再交给后台

### Scheduled Tasks适合重复任务

桌面端可以创建定时任务，在本地项目目录或隔离的 Worktree 中周期执行。适合：

- 每天检查新出现的依赖漏洞，只生成报告；
- 每周汇总仓库变更和测试趋势；
- 每小时扫描一批导入文件，输出命名建议；
- 定期运行文档链接检查，把失败项整理成待办。

第一次创建后要立刻手动测试一轮，确认工作目录、权限、网络、输出位置和失败提示。计划任务没人盯着，更要避免宽泛目标和不可逆动作。

下面这个任务比“每天检查项目”更容易验收：

```text
工作日18:30检查当前项目过去24小时的变更：
1. 读取git log和测试报告；
2. 按功能、修复、测试、文档四类汇总；
3. 如果测试失败，列出失败用例和日志位置；
4. 只生成Markdown报告到reports/daily，不修改源码，不提交，不推送。
```

:::warning 截图提示：Scheduled Tasks创建与运行历史
建议放两张截图：一张标出计划时间、工作目录和权限；另一张展示某次运行的状态、输出和失败信息。
:::

### Remote适合查看和接续，权限仍在电脑端

远程能力可以让你从手机或另一台设备查看任务、发送后续指令和处理审批。它更像把当前工作现场延伸到另一块屏幕。项目文件、命令环境、已安装工具和本机权限仍然属于运行任务的那台电脑。

远程使用前至少确认：

- 电脑端是谁的账号和工作区；
- 当前任务在哪个目录；
- 哪些操作仍会等待审批；
- 电脑离人以后是否允许保持唤醒；
- 手机丢失或设备不再使用时从哪里断开连接。

## 常见问题排查

### 安装后提示codex: command not found

按这个顺序查：

1. 关闭终端并重新打开；
2. 重新看安装脚本结尾的 PATH 提示；
3. 执行 `which codex` 或 `command -v codex`；
4. npm 安装时执行 `npm prefix -g`，确认全局可执行目录；
5. 检查是否在另一个 Shell、WSL 或远程主机里安装；
6. 修好 PATH 后再跑 `codex --version`。

### 登录浏览器完成了，终端还在等待

先等几秒，确认浏览器最后显示成功。仍然没返回时：

- 检查终端进程有没有被关闭；
- 企业代理或安全软件是否拦截本地回调；
- 用 `codex logout` 清理旧状态，再执行 `codex login`；
- 运行 `codex doctor` 获取认证诊断；
- 别把登录回调链接发给别人代开。

### Codex一直请求权限

先看请求是否都在访问同一个工作区外目录。如果确实需要另一个目录，可以把任务启动位置调整正确，或按当前版本提供的方式增加可写目录。别为了省掉几次确认直接打开 Full access。

如果是网络请求，检查任务为什么需要联网。安装依赖、读取官方文档和调用外部服务的理由不同，对应的风险也不同。

### Codex改错了文件

立即告诉它停止继续修改，先执行 `git status --short` 和 `git diff`。未提交改动里可能混有你自己的内容，不要随手运行清空整个工作树的命令。

可以让 Codex 先列出“本轮由它改动的文件”和“开始前已经存在的改动”，再逐项决定如何回退。重要项目在开始前做 Git 检查点，会省掉很多辨认工作。

### 对话越聊越乱

先暂停增加新需求，让 Codex 用四个栏目整理：当前目标、已确认决定、已改文件、剩余问题。核对无误后 `/compact`，或者把摘要带进 `/new` 开一个干净会话。

如果目标已经换了，直接新会话更省事。让一个装满旧实现细节的会话突然改做另一套系统，通常只会继续带着无关假设。

### 测试通过了，页面还是不对

确认测试覆盖了你看到的问题。单元测试通过，只能说明测试里写到的行为通过。页面还要检查浏览器控制台、网络请求、真实视口、键盘操作和数据边界。

把截图、复现步骤和期望结果一起给 Codex：

```text
375px宽度下，筛选按钮把页面撑出了横向滚动。
附件是当前截图。请先用浏览器复现并定位具体元素，修复后给出修改前后的视口宽度和验证截图。
```

## 第一次上手的验收清单

完成一次任务后，按下面的清单走一遍：

- [ ] Codex 当前工作目录正确，没有把个人主目录当项目；
- [ ] 开始前看过 `git status`，知道哪些改动本来就存在；
- [ ] 权限模式与任务风险匹配，没有无理由使用 Full access；
- [ ] 需求包含目标、现场、边界和验收；
- [ ] 安装的新依赖能说明用途和来源；
- [ ] `git diff` 的文件范围符合预期；
- [ ] 测试、构建或页面验证由实际命令和结果支撑；
- [ ] 没有把 API Key、Token、个人路径或账号信息写进文件；
- [ ] Codex 没有替你提交、推送、发布或修改外部系统，除非你明确要求；
- [ ] 剩余风险和未覆盖项已经写清楚；
- [ ] 出问题时知道怎样按文件或小范围改动回退。

第一次练习做到这里就够了。接下来可以挑一个你真正熟悉的小需求，把四段式任务说明写好，再完整跑一遍。你越了解项目本身，越容易判断 Codex 的分析有没有跑偏，也越容易把一轮好结果整理成团队能复用的 `AGENTS.md` 或 Skill。
